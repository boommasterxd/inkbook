# Bounded Performance Measurements

> Historical decision, superseded by [Deterministic Performance Checks](deterministic-performance-checks.md). Timing commands and comparison rules below are no longer active.

## Decision

Run all candidate capacity, correctness, resource, and scheduling contracts once per classified profile before comparing speed. Use their timing evidence to select exact file/test scenarios. Never infer successful coverage from omitted or malformed evidence. Scenarios must own their fixture state.

Use exactly six paired processes, with three AB and three BA orders declared before measurement. Require six of six ratios strictly below or above the 1.20 boundary to decide pass or regression. Other valid evidence warns; regression and execution/evidence errors fail. There is no automatic second stage. This supersedes the initial six/twelve plan described in historical validation below.

The expensive domain transform, maximum-pressure-stroke, and Clipboard scenarios use one measured run per process instead of five in measurement mode only. Keep the original domain warmups and action populations: 50 measured 10,000-stroke transforms and 20 maximum pressure strokes. Clipboard retains 20 measured copies plus 20 pastes, with one complete warmup of each operation in measurement mode and the original twenty in reference mode. Clipboard emits one worst-run p95 per operation; full reference mode retains five runs and equivalent original budgets. Full domain contracts retain all five runs; Clipboard contracts retain five single-action runs, keeping metric identities stable across modes. This reduces temporal coverage, not fixture size. Full and order-only exports use five measured operations each instead of twenty; incremental exports retain all one hundred. The existing p95 estimator becomes the maximum of five full/order-only observations, while reference mode retains 20/100/20 samples. Export warmup and exact acknowledged/prewarmed runtime state remain unchanged.

Remove redundant unmeasured setup: execute the exact-base callback's full save lifecycle once, retaining one callback warmup and five timed real callback invocations with fresh string copies. The callback reads constant closure state and mutates none before the enclosing process completes. Pressure-group static matching uses a deterministic serialization-setup hash because the measured matcher consumes no metadata hash.

The snapping scenario creates only its own dense-target store, without constructing an unused standard-domain store. Maximum viewport strokes construct their final typed points directly, without first allocating and discarding a second point array. Their returned fixtures and measured populations remain unchanged.

Keep the two existing runners and twenty-minute hosted job ceilings. Move Clipboard, exact-base-save-callback, and pressure-group-integrity invariant files to the refresh-profile shard at 120 Hz; the shared shard keeps the other invariant and all budget-only files. The local run executes their exact union. All five cadence contract profiles remain.

The canonical policy is in [Performance CI](../performance-ci.md). More extensive diagnostics are manual; this decision adds no recurring job.

## Rationale and Limits

The previous whole-file six/eighteen-pair scheme nested repeated processes around expensive repeated actions. One inconclusive metric could repeat an entire mixed file. The focused Core-file run still exceeded twenty minutes even after removing unrelated export comparisons.

The new plan reduces work but can leave more uncertainty and miss slowdowns that the longer population would resolve. The per-metric one-sided false-pass bound for six unanimous signs is `1/64 = 0.015625`, assuming independent signs with null probability at most one half. This is not a guarantee across all metrics or against merging a real regression: warnings remain nonblocking. No percentage or timeout is widened.

## Verification Requirements

Verify exact scenario matching, failed/skipped/missing evidence, state independence, exact six-pair decisions, and disjoint hosted coverage equal to the complete local run. Run unchanged-code controls and targeted slowdowns, including sparse action-tail delays, with the fixed population chosen before measuring. Preserve raw results and report unresolved evidence. A hosted Core-input control must measure actual comparisons; a source-identity skip proves neither noise stability nor runtime. Completion of one selected control does not establish the full-suite worst case.

## Measured Validation

Before the current six-pair revision, fresh local Node.js 26 paired controls used the predeclared six/twelve plan and exact scenario selection. The five live-stroke metrics finished with four passes and one inconclusive result after twelve pairs, without a detected regression. Adding 1 ms to two of 120 actual renderer handoffs in an isolated disposable source tree produced a p99 regression after six pairs.

The changed 50-action transform population was separately controlled at 240 Hz: three metrics passed and one remained inconclusive after twelve pairs. Adding 20 ms inside the actual time-sliced transform operation in a disposable source tree produced two regressions after six pairs, including materialization ratios of approximately 1.51 to 1.67. The other metrics were one pass and one inconclusive result. Neither mutation changed the tracked production source. These are targeted local sensitivity checks for clear slowdowns, not proof of reliably detecting a slowdown just above 20 percent or every rare pause.

A replay of earlier stored measurements also retained ten inconclusive unchanged-source profile cases without a regression and detected five sparse 0.25-ms handoff mutations after six pairs. It is retrospective supporting evidence, not a fresh whole-suite control.

The first hosted Core-input control of this plan completed cadence comparisons in 8m30s but still timed out the shared job during its tenth budget pair. Its budget measurement batches fell to approximately 51 seconds initially and 34 seconds for unresolved scenarios, but retained unrelated pressure/geometry scenarios through shared test imports. Those existing scenarios were subsequently separated without changing their action populations or assertions. The unsuccessful run remains part of the evidence; reducing repetition alone did not meet the runtime objective.

The subsequent [hosted Core-input control](https://github.com/boommasterxd/inkbook/actions/runs/35279877389) completed quality in 4m02s, shared performance in 18m38s, and refresh performance in 10m24s. Shared produced 35 passes and 12 inconclusive metrics; refresh produced 24 passes and 13 inconclusive metrics. Neither shard reported a regression or contract/evidence violation. A comment appended only inside the disposable runner's Store file triggered normal changed-input selection without changing executable source; no diagnostic Store change was committed. Both comparisons reached the fixed twelve-pair stage. This validates that selected Core control, with only 1m22s of shared-job headroom, not the all-files worst case or a guarantee against slower hosted runners.

The [full-input diagnostic](https://github.com/boommasterxd/inkbook/actions/runs/35336836868) then exposed a Clipboard metric-cardinality bug: contracts emitted two records while measurement emitted ten. Shared failed closed after 5m47s, with one full invariant measurement side taking 158 seconds. Refresh completed in 9m54s with 40 passes, 20 inconclusive metrics, and no violations. This invalidated any general runtime claim from the earlier Core-only control and motivated the current fixed-six plan, Clipboard aggregation, and workload partition.

Before shortening the Clipboard warmup, the fixed-six one-run population was validated with fresh local Node.js 26 pairs using the same twenty-action runs and warmups. Both unchanged-source metrics passed, with all ratios between approximately 0.97 and 1.01. A disposable-source mutation added 1 second to every tenth call of the shared encoding/canonicalization boundary, delaying two of twenty measured copy actions and two of twenty measured paste actions. Both p95 metrics regressed after six pairs: copy ratios were 4.38–4.44 and paste ratios 3.82–3.93. No tracked production source changed. This establishes detection of that clear sparse slowdown, not sensitivity just above 20 percent or every rare pause.

The next [full-input run](https://github.com/boommasterxd/inkbook/actions/runs/35341084972) still timed out both jobs. Shared completed all invariant pairs at roughly 42 seconds per side and five budget pairs at roughly 49 seconds per side. Refresh completed only four invariant pairs and one additional side at roughly 103 seconds per side, before starting cadence comparisons. These failures motivated the final setup reductions and declared warmup/export populations above; fixed six pairs and workload redistribution alone were insufficient.

Fresh local Node.js 26 validation of the final populations and callback setup used six predeclared balanced pairs per experiment. All six unchanged-source metrics passed (ratios approximately 0.94–1.06). Separate disposable-source delays targeted the shared Clipboard codec (1 second every tenth call), full/order-only worker execution (500 ms per operation), and the exact-string comparison used by the real save callback (5 ms per invocation). All five targeted metrics regressed after six pairs; the untouched incremental export metric passed. Clipboard delays affected two of twenty measured actions per operation. The mutations were discarded and did not modify tracked runtime code. These are clear-slowdown sensitivity checks, not guarantees for small or rare regressions.

The subsequent [full-input control](https://github.com/boommasterxd/inkbook/actions/runs/35343184829) completed refresh performance in 18m58s with 33 passes and 31 inconclusive metrics, but shared performance again hit the twenty-minute timeout. Budget measurement sides took about 69 seconds, versus about 49 seconds in the preceding run. The runtime objective remains unmet; local correctness and slowdown detection do not establish hosted completion.

A separate [single-round cost diagnostic](https://github.com/boommasterxd/inkbook/actions/runs/35345413186), explicitly not an acceptance gate, measured shared invariant and budget batches at 40.7 and 71.8 seconds. At those observed costs, twelve sides alone require approximately 22.5 minutes before contracts and setup. The largest measured scenario costs were worker export (29.3 seconds), selection handoff (15.5 seconds), and large transforms (13.3 seconds). Refresh invariant and cadence batches took 54.5 and 24.6 seconds. These measurements precede the two small fixture-only optimizations above and establish no successful full-suite runtime bound. Further reductions require an explicit population/coverage or runner-allocation trade-off; do not report the current configuration as meeting the full-input twenty-minute objective.
