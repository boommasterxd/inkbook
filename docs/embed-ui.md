# Handwriting Embed UI

## First Appearance

While a syntactically valid standalone custom embed resolves to an SVG whose recognition is pending, replace its Markdown text immediately with a neutral loading placeholder whose outer height grows from zero to 48 CSS pixels over 180 milliseconds with the automatic-page-growth smoothstep interpolation. The lifecycle-owned placeholder is visually blank until the shared [loading indicator](#loading-feedback) is due. It has an accessible group label, uses the canonical page surface, and never imports unvalidated SVG markup. Failed recognition restores the original Markdown presentation; disposal prevents a late result from mounting a preview. Live Preview snapshots the source path and mode with its decorations so an in-place host-context update rebuilds the placeholder in the same editor transaction, before asynchronous recognition completes.

An existing embed in a newly opened note reveals its actual outer block height from the currently rendered loading-placeholder height to the measured locked-preview height. Recognition that finishes during placeholder growth transfers that intermediate height, including zero, without first jumping to 48 pixels. Live Preview retains the current height across pending-widget remounts; lifecycle disposal cancels the old animation before it can write further heights. A cached preview that did not display a placeholder starts at zero. Both growth and shrink use the same interpolation. Live Preview and Reading view use the same presentation lifecycle. After the native scrollbar lease and a positive settled width are available, the reveal uses the automatic-page-growth duration of 180 milliseconds and the same smoothstep interpolation. The validated preview remains at its natural size; only the outer root height and temporary clipping change. The shell does not fade or scale, and following Markdown moves with the growing block.

A newly inserted embed queued for automatic activation holds its current loading-placeholder height while the editable document and first active scene are prepared. It then reveals directly to the editor height in one 180-millisecond smoothstep, without an intermediate locked-preview height transition. Only the canvas is clipped during this initial active reveal; the toolbar retains its existing independent opening animation. The shared delayed loading feedback may grow a held zero-height presentation to the 48-pixel loading height; readiness continues from its actual current height. Failure, timeout, or cancellation resumes the preview reveal, and early locking retargets the current height to the locked preview. Manually opening an already presented locked embed retains the ordinary unlock transition.

The fixed root height and clipping are removed at completion. Host measurements are deferred during the reveal and refreshed afterward. For an automatically activated insertion, scroll stabilization remains leased until that reveal finishes, even though toolbar readiness is announced at its start. A width change retargets from the current revealed height. Reduced motion skips interpolation, including when enabled during the reveal. Detaching cancels pending animation work and resolves presentation readiness without mounting an editor.

Document loading may proceed concurrently with the reveal, but active-scene construction waits until it completes. The runtime then rechecks the active session and attachment before starting the existing locked-to-active transition. A click during the reveal waits for the measured presentation instead of interrupting it with a second height animation.

Appearance belongs to each embed occurrence, not to its SVG file. Preview refreshes, edits before the embed, and CodeMirror viewport remounts retain that occurrence's state instead of replaying the reveal. An interrupted preview reveal retains its current outer height and resumes from there; the occurrence is marked presented only after successful completion. Opening a different note resets the state. Live Preview retains at most 4,096 occurrence states per note view; additional untracked occurrences display immediately until capacity becomes available.

## Loading Feedback

Recognition, initial presentation, and automatic editor preparation use the same icon-only `Loading drawing` status. The placeholder starts growing immediately; its spinner appears only after 500 milliseconds and a following animation frame, measured from placeholder creation rather than animation completion. The frame rechecks that loading is still pending, so a fast completion never flashes an indicator. Loading and saving indicators use the host's `--interactive-accent` color on a 40-pixel circular `--background-primary` surface with a host-theme border and restrained shadow. They stay centered in the embed's visible native-scroll intersection. Reduced motion keeps the icon static. The spinner follows the presentation's effective motion preference, including changes while it is visible: enabling reduced motion stops rotation, and restoring full motion resumes it. An explicit full-motion preference continues to override the system reduced-motion setting.

Build the indicator detached and measure its initial position before mounting its fixed, pointer-transparent host in the owning document's body. Viewport coordinates keep it outside the native scroll compositor, so scrolling cannot displace it before the next position update. Read presentation and native-scroll bounds before writing feedback styles. Coalesce scroll and resize updates through the owning window's central scheduler at input priority; indicator positioning has no CSS transition. Detached placeholders retain an unmeasured-center host inside the presentation until it can be measured, then move that same host to the body. The host follows the presentation's scheme and motion settings. Disposal removes it and releases pending work, observers, and listeners.

The manual-opening `Loading drawing` overlay waits 250 milliseconds and a following animation frame that rechecks pending work, including a click during the initial preview reveal. Completion before that frame cancels the overlay entirely, without an intermediate border, dimming, or blur. If still pending, the backdrop enters over 220 milliseconds and the spinner enters over 120 milliseconds, with the shared standard easing.

Once a manual-opening overlay appears, its visual lifetime lasts at least 250 milliseconds before the complete spinner/backdrop surface fades out together over 220 milliseconds. This avoids a brief dark flash when readiness follows shortly after the threshold. Time already spent showing the overlay counts toward the minimum; a longer load adds no further hold. Editor readiness, input, focus, and status accessibility update immediately: the retired visual is pointer-transparent and hidden from assistive technology while its remaining minimum and exit finish. It can therefore briefly cover an already usable editor. Failures, cancellation, replacement, disposal, and a change to reduced motion bypass the visual hold. Reduced motion settles transitions immediately. Recognition and automatic activation retain their separate 500-millisecond deadline.

The decorative, pointer-transparent black backdrop at 52 percent opacity dims only its presentation and applies a 3-pixel backdrop blur, following the embed's bounds and rounded corners. It starts with the delayed indicator. The separate status surface stays sharp above the dimmed drawing. Full Motion fades the complete dimming and blur layer in and out over the shared 220-millisecond surface duration and standard easing. Recognition, automatic activation, and saving remove their status immediately at completion; manual opening retains only the retired visual as specified above. Reduced motion settles the backdrop immediately, including a preference change before the spinner exists or during a fade. Replacement and disposal cancel and remove the layers synchronously.

The placeholder's monotonic start time transfers once to the presentation attachment. Its occurrence state retains no feedback object or DOM reference. If the threshold has already elapsed, the new presentation shows the same indicator immediately instead of scheduling a second delay. Automatic activation takes over that loading handle until the active scene is ready; preview-only loading ends when the measured entrance finishes. Cancellation, replacement, failure, and disposal finish owned feedback. Manual activation starts a fresh overlay interval instead of inheriting a recognition delay. There is never a separate visible loading-text phase or two indicators on one presentation.

## Locked State

In the locked state, no interactive drawing area is mounted. The embed displays a static preview of the saved SVG file.

Clicking the preview unlocks the embed.

The following rules apply:

- Only one ink embed can be active at a time.
- When another embed is opened, the plugin saves and locks the previously active embed.
- The locked preview and active scene occupy the same lifecycle-owned inline block. Unlocking never appends a second editor before or after that block.
- An empty locked preview contains at least 2.5 writing lines, rounded up to the next complete writing row, plus the writable SVG margins. Obsidian's generic button height MUST NOT override this intrinsic preview height.
- A non-empty patterned locked preview contains the complete pattern row holding the lowest annotation, exactly one further pattern row, and the writable bottom margin. A preview without a visible pattern uses one trailing 100-unit writing row. It never retains the active writing buffer or a persisted locked-buffer multiplier.
- The existing preview remains visible until the in-place editor has fully loaded and has been measured correctly.
- Every validated locked preview carries its persisted revision and SHA-256 output hash. Live Preview replaces an otherwise equal widget when that identity changes, while Reading view refreshes its lifecycle-owned surface from only the latest matching recognition result. Unlock carries the identity of the preview currently shown and compares it with the independently validated file before Store adoption. A mismatch publishes no editor, refreshes the locked preview, and presents persistent `Retry` and `Keep saved preview` recovery with an explicit version-change warning.
- Activation is never delayed merely to show [loading feedback](#loading-feedback). While validation has not yet produced a trustworthy `activeHeight`, the presentation remains at its exact locked height instead of guessing a target, and the complete locked preview remains visible beneath any shared loading indicator.
- After layout and the first complete active-scene commit have been measured and painted behind the locked preview, the preview becomes hidden and any mounted `Loading drawing` status retires from accessibility in the frame that exposes the active scene, foreground, toolbar, and input. Manual-opening feedback may retain its pointer-transparent visual under the [minimum-display contract](#loading-feedback); other loading status surfaces disappear immediately. The same block then grows from the serialized `lockedHeight` to the derived `activeHeight` over 240 milliseconds with the shared immediate-start `ease-out` curve. Its top edge, width, root, and document position remain anchored; no second editor is inserted and toolbar chrome contributes no block height. The completion step removes the already hidden old preview and temporary clip geometry.
- One persistent outer shell owned by the embed root draws the page surface, border, dynamic radius, and clipping edge in both states. Neither the locked preview nor the active editor owns a visible duplicate shell.
- Before the first growth frame, a fresh renderer commit after the final initial layout is required; an earlier commit cannot release the preview. During preparation and unlock, renderer culling uses the final content height while retaining the live native-scroll-owner intersection, instead of following the animated clipping height. The active SVG scene is laid out once at its final `activeHeight`, remains top-anchored at that fixed block size for one complete painted frame behind the locked preview, and includes background-pattern coverage for the complete prepared envelope. The active editor and old preview exchange visibility atomically when growth starts. During the transition, the scene stays unchanged while only the rounded background container grows and clips progressively more of the already rendered scene and pattern. Its physical and logical block-start inset, transform origin, and page-space origin remain at the container's top edge; it is never vertically centered. Viewport clipping during these 240 milliseconds MUST NOT rebuild or realign the background per frame. The representation swap never changes shell opacity, background, border, or radius. The hidden old preview remains lifecycle-owned until transition cleanup, so cancellation can restore it safely; there is no frame in which both inner presentations are hidden or detached.
- Automatic page growth may occur later when committed content leaves less than one aligned writable line.
- With reduced motion, measurement is still awaited, then target height and preview/editor visibility are applied without interpolation.
- If reduced motion becomes effective during an unlock, the transition resolves to the validated active height and completes the preview-to-editor handoff; it never finishes at an intermediate height. If the first complete scene commit is still pending, the locked preview remains visible until that proof is available.

This prevents an empty, incorrectly scaled, or partially initialized drawing area from appearing briefly.

Locking keeps the disabled editor visible while the exact persisted preview is restored as a lower, already complete layer. After one complete paint opportunity, the inner representations exchange atomically in one frame and the editor unmounts. The persistent outer shell is never transparent or replaced.

## Unlocked State

The active editor consists of:

- the outer embed frame
- the floating toolbar
- the SVG drawing area
- the background
- the committed elements
- a temporary live stroke
- selection and cursor overlays

The border, rounded background container, toolbar, focus treatment, and menus use Obsidian variables from the active host theme. Focus rings appear after Tab or navigation keys within the toolbar or adaptive panel. Pointer contact, insertion, programmatic focus, canvas tool shortcuts, and modified keyboard shortcuts do not initiate focus rings. Adaptive panels preserve the opening navigation mode and retain accessible focus management. The embed focus ring sits inside the outer shell with the same radius, independently of clipped preview and canvas layers. The document graphic inside the container uses Inkbook's fixed, self-contained light and dark palette so the saved SVG and active scene remain identical outside Obsidian. The palette and scheme lifecycle are defined in [Standalone SVG Envelope and Theme Rendering](svg-envelope.md).

Its appearance:

- 1-pixel outer border
- gray Obsidian surface
- rounded background-container corners
- dynamic radius of `clamp(10px, 2% of the embed root content width, 20px)`; measure the persistent root in both states, never a retained editor child, and retain the last valid radius while the root has zero width
- no additional internal CSS padding
- the visible unpatterned margin on all four sides is part of the SVG page, scales with it, and is writable

The SVG page itself is not rounded. The background container provides the dynamic corner radius and clips the SVG at its corners. The rounded background remains visible below the toolbar. The top, right, bottom, and left page margins are embedded directly in the SVG rather than being created by a separate frame or CSS padding. Background guides stop at the inner edge of those margins, while the input surface and element renderer cover the complete page. Writing into a margin is therefore retained, and downward growth restores a complete bottom margin below the new occupied extent.

The normative DOM layer hierarchy is:

1. The embed root owns measurement and relative positioning but does not clip descendants.
2. A zero-height sticky host is the first child of the active editor. The toolbar is an absolutely positioned overlay lifted above that host and therefore contributes no layout height.
3. The background container owns the border, background, radius, and clipping.
4. The SVG committed-content bands and decorative overlays are inside the clipped background container and use `pointer-events: none`.
5. One transparent, focusable canvas input surface is above that content, below the toolbar and host menus, and owns canvas pointer, wheel, context-menu, and keyboard events.
6. Inkbook mounts its menus in the owning document so they are not clipped by the background container and remain correct in pop-out windows.

Activation preserves the root, top-edge anchor, measured width, presentation attachment, and active editor identity while intentionally animating the block from `lockedHeight` to `activeHeight`. The toolbar overlays the note immediately above the page, including Markdown already painted there, and does not move that content or reduce, cover, or pad the SVG page. The embed root explicitly preserves visible overflow and disables host-imposed paint containment so the upward toolbar overhang remains painted and hit-testable; paint containment remains scoped to the page surface below it. A stroke commit, autosave, SVG resource refresh, theme change, or asynchronous document reclassification MUST NOT detach, remount, move, or lock the active editor.

The outer shell uses its own persistent embed-root content-box width after the resolved note scroller's native right-hand scrollbar gutter has been stabilized. The editor independently measures its background-container content box for page layout and width-fit zoom. Both respect note padding, readable-line width, lists, callouts, and other nested constraints; they never adopt the full scroller width. No Inkbook layer, including the toolbar, input surface, focus treatment, or background container, extends over the owner client edge or scrollbar gutter. Pointer contact does not add or remove any layout-affecting UI. The host-scroll ownership, edge clamp, and platform-specific native overlay behavior are defined in [Obsidian Integration](obsidian-integration.md#native-scroll-owner-and-scrollbar-stability).

## Optional Quick Tour

The tour uses the normal editor paper without a covering wash. Its temporary extra height follows the renderer's [presentation background coverage](rendering-and-performance.md#background-geometry-cache), so the configured grid, lines, or dots continue through the reserved tour area without changing the saved page.

The final step points back to More options and explains that Settings lets users personalize tool defaults, paper, input, and other preferences. It follows the four context actions, making sixteen steps in total or seventeen when Finger drawing is available. It is informational and does not open settings automatically.

The first ready active embed on a device and vault offers the handwritten question `do you want to` / `start a tour?` on two lines directly on the paper. The invitation renders into that paper through its owned React portal, outside the sticky toolbar's shadow surface. Its check and X icon actions, named `Start tour` and `Skip tour`, never take focus automatically, disable drawing, create a document, or modify ink. The invitation is consumed when first offered, so ignoring it, dismissing it, leaving the note, or restarting Obsidian does not cause repeated invitations. The durable device preference is defined in [Settings](settings.md#onboarding-preference).

Starting the tour explicitly draws a sequence of short notes on the canvas. The steps follow the physical toolbar from left to right: optional Finger drawing, Undo and Redo, Select with lasso or rectangle, Eraser, Draw, Highlighter, Straight highlighter, Active shape, Shape picker, Style, Lock, and More options. Paste, Copy, Cut, and Delete follow as context actions before the final settings hint. Finger drawing appears only when its toolbar control is available. The tour preserves the active tool and real selection. A curved arrow starts six CSS pixels beside the painted title edge at its vertical center and sweeps upward to the actual toolbar icon. The note moves beside its target when there is room; navigation stays independent of the note. The title's native SVG geometry is measured once per step; positioning projects those cached bounds through the current SVG screen matrix without inspecting document ink. The connected arrowhead follows the final vertical curve tangent. The title and caption use original handwritten cubic pen trajectories reused from the README artwork. Each pen stroke draws in order; the implementation neither reveals a font outline nor creates editor-domain strokes. The readable text and controls are accessible immediately. Reduced motion displays the complete strokes immediately, including when enabled during drawing. The note is a non-modal dialog on every platform, with an unboxed paper appearance and no phone sheet or icon ring. Decorative SVGs are hidden from assistive technology; a named text equivalent identifies the control and explains its operation.

For readable lettering, the presentation temporarily reserves a minimum paper height of 220 CSS pixels for the invitation and at least 360 for the tour. The tour minimum grows with the measured note and navigation content when needed, reserving space for the current instruction. Full Motion owns this explicit minimum-size transition; the document dimensions, geometry, camera, history, and SVG remain authoritative and unchanged. Its origin is the current visible block size; restoration targets the layout owner's explicit block size or the original minimum, whichever is larger, before restoring the original minimum property. This keeps the visible height moving throughout the transition instead of animating an invisible minimum below the normal page height. On explicit start and viewport resize, the tour reveals insufficiently visible paper through the existing native scroll owner. The usable region intersects that owner's client bounds with the visual viewport and safe-area insets. On phones, inherited navbar and mobile-toolbar height and bottom-offset tokens reserve space even while the native bar is hidden; no private host selectors or host DOM traversal are used. Obsidian remains the sole vertical scroll owner. Toolbar targets and the eventual focus-return control are revealed horizontally without moving the note vertically. The tour layer is a child of the paper, clipped at its rounded boundary. Arrows sweep upward with a vertical final approach and an upward-pointing head beneath the actual toolbar icon; no teaching ink extends into the toolbar or surrounding note. The note and arrow disappear when that paper is scrolled away. The normal editor surface, including its configured paper pattern and existing ink, remains visible throughout the tour. Layout reads are coalesced through the owning window's WorkScheduler and never visit the element store or ink nodes.

When the usable viewport is shorter than 400 CSS pixels, a compact variant places the heading above two side-by-side caption lines in a note up to 560 pixels wide. It uses 24-pixel title and 20-pixel caption SVG boxes and a shorter arrow. The step counter moves beside the navigation pill without wrapping or shifting its center; targets retain their full 44-pixel size. Navigation sits four pixels inside the lower usable paper edge with four pixels of instruction clearance, while the regular variant retains its 16-pixel inset and 24-pixel clearance. The phone viewport also reserves the inherited view-header height above the paper and toolbar. Navigation visibility is independent of instruction height and target availability: a temporarily clipped instruction or asynchronously mounting toolbar target cannot hide Next or Skip. If native resize anchoring subsequently clips the instruction or toolbar target in partially visible paper, the existing coalesced positioning pass reveals them again and schedules another pass only after an actual scroll correction. An unchanged or clamped scroll does not create a frame loop; entirely offscreen paper is not pulled back. Intentional wheel, touch, or keyboard scrolling suspends correction until the next tour step or viewport resize. Rotation reuses the same mounted controls and current step without replaying the invitation or resetting progress.

The compact navigation toolbar uses the paper surface and existing host border token. It contains circular `Back`, `Next` or `Done`, and `Skip tour` icon buttons, with a dynamic step count centered above the pill. The navigation remains mounted and centered at the lower visible paper edge, 16 CSS pixels inside it, independently of the moving note. It does not tween its position, and the note keeps a 24-pixel clearance above it. Each button retains a transparent 44-pixel hit area and shares the primary toolbar's inset-surface feedback: the host hover color and a 0.92 press scale, returning over the shared 120 ms transition. Press also paints that neutral surface for touch and keyboard input. Release, cancellation, window blur, and disabled-state changes clear transient feedback. The navigation keeps its neutral keyboard-focus outline and neutral icon color. Back is disabled on the first step. Every action has a 44-pixel minimum target and an accessible name. These controls, Escape, and outside dismissal provide navigation and exit without requiring drawing or a tool action. A click on the canvas or a real tool dismisses the guide and retains that control's normal operation. Completion and dismissal return focus to the invoking toolbar control or canvas while preserving deliberate new focus. On exit, the guide layer immediately becomes inert and hidden from assistive technology, and input ownership, observers, listeners, and scheduled work are released. The layer fades out using the shared 220 ms adaptive-menu transition; only after the fade completes does the paper minimum animate back to its original value over 220 ms. Immediate disposal and reduced motion bypass the applicable transitions. Locking, detach, and unload release the remaining guide resources. Completion and dismissal do not lock the editor or mutate the document; extra paper height is presentation only. `Quick tour` in `More options` can always reopen the tour explicitly, independently of the invitation preference. The menu closes before the tour opens, including on phones. Instruction and invitation content belong to application chrome and never enter history, autosave, clipboard data, or SVG output.

During the four side-action steps, a presentation-only preview flag makes Paste, Copy, Cut, and Delete visible through the existing toolbar composition, on the configured handed side. Preview buttons retain their normal appearance but are natively disabled, excluded from keyboard navigation, and described by their real prerequisites. They cannot execute actions; pressing a preview keeps the guide open. The tour does not manufacture a selection, read or write the clipboard, or change document history. Leaving these steps, skipping, finishing, and disposal clear the flag and restore real availability. Toolbar-only mutation and resize observations handle asynchronous preview mounting and bounded position changes; they never observe document ink. Horizontal target reveal uses only the plugin's own context and primary scrollports.

Vertical reveal clearance includes the measured target offset above the paper, so the taller context buttons retain their complete hit area below the host header as well.

## Toolbar Layout

The primary toolbar is one continuous control track. Context-sensitive clipboard and deletion actions are separate circular controls placed to its right by default and mirrored to its left in left-handed mode. They never participate in centering the primary track.

The general actions are located at the start of the primary track:

- finger-drawing toggle when finger drawing is enabled for this device and vault
- Undo, always visible and disabled when no action can be undone
- Redo, always visible and disabled when no action can be redone

The tools are located in the center:

- Select
- Eraser
- Draw
- Highlighter
- Straight Highlighter
- Active Shape, displaying the currently selected shape icon
- Shape Picker
- Style

The Straight Highlighter control uses the same marker silhouette as Highlighter with two short, evenly spaced ruler marks inside the body instead of a generic line symbol. Inkbook registers this custom icon through Obsidian's public `addIcon()` API and removes it on plugin deactivation through `removeIcon()`.

The Style control retains the canonical 19-pixel Palette geometry instead of swapping among stored icon assets. Its SVG attributes update from the active tool defaults: the glyph outline uses the tool color, line-cap-safe dash patterns distinguish solid, dashed, and dotted outlines, and a closed shape fills the palette body with its fill color and exact fill opacity. The four palette wells stay solid and use the outline color. The SVG node and button remain mounted while these attributes change, and Theme text color resolves through the owning toolbar's current host color in every window. Because Style opens the lifecycle-owned adaptive panel, its trigger exposes `aria-haspopup="dialog"`; Overflow, Shape, and context-menu triggers expose `aria-haspopup="menu"`.

Pressed toolbar controls transition their foreground color to the host accent over the shared 120-millisecond style-change duration while their pressed semantics update immediately. Selecting a Style choice likewise updates its checked state immediately and animates its selected background, border, and foreground in place; it does not close or recreate the panel.

Toolbar color motion receives explicit numeric RGBA values from the shared browser palette. The palette resolves host theme colors in the owning document before passing them to Motion, so interrupted color changes retarget from a concrete color value. Main-window and pop-out toolbar buttons use the same press feedback: pointer cancellation, lost capture, release, and owning-window blur clear a pressed state; Space and Enter provide keyboard press feedback without delaying the button's normal activation.

Shape and Select toolbar glyphs crossfade when their selected shape or selection mode changes; their labels and accessibility state update immediately. The Style panel's Pressure sensitivity switch keeps its initial visual paint synchronized before the first activation, then animates its track color and thumb position over the shared 120-millisecond duration while the checked state changes immediately. Owned settings, shortcut, and action-dialog control subtrees use the same feedback for native controls, including controls added or replaced after mount, and release their listeners with the owning view without binding a control twice. Shortcut recording text and its polite status message crossfade over the same duration while recording and announcement state update immediately. Error messages use the shared danger text tone for readable contrast. Motion projects the existing recorder button, status surface, and following setting rows through their actual DOM refs in one layout group; native control identity and focus remain stable. The host-owned General settings toggles retain Obsidian's native styling and feedback.

The end of the primary track contains:

- Lock
- overflow menu

Context-sensitive actions appear as separate circular controls on the handedness-selected side of the centered primary track, ordered from the primary track outward:

- Paste
- Copy
- Cut
- Delete

Copy, Cut, and Delete only appear when there is an active selection. Paste appears when `Clipboard.read()` is supported or a validated in-session payload exists, and occupies the context-action position nearest the primary toolbar. This capability-based availability does not inspect system clipboard contents or permission; the complete supported Blob representations are requested only after an explicit Paste action. Once visible, Paste remains mounted, enabled, and visually unchanged while another Clipboard operation is pending instead of replaying its presence animation; repeated input receives bounded busy feedback. Undo and Redo remain visible at stable positions for the complete active-editor lifetime; each is disabled, removed from sequential and roving keyboard focus, and visually muted when its corresponding action is unavailable. Appearing or disappearing context controls MUST NOT move the primary track away from the exact editor center or change the toolbar layout stage. While the primary track plus its fixed minimum side corridor fits, excess context actions scroll only inside the handedness-selected side corridor. The complete toolbar becomes one scrollable row only when the primary track plus that fixed corridor no longer fits.

The overflow menu opens through an Inkbook-owned menu below the three-dot trigger and never at the canvas center. On desktop and tablet, its measured rendered width is centered over the three-dot trigger and clamped to the visible viewport. Its icon-labelled Background item previews the active None, Lines, Dots, or Squares pattern and hands off to Inkbook's shared adaptive panel after click, touch activation, Enter, or Space. The Background panel begins with an icon-labelled Back action and exposes the same four choices without a redundant heading. Choosing a pattern updates the checked state and optional spacing control in place without closing or recreating the panel. Back returns to Overflow using the platform-specific [panel navigation lifecycle](obsidian-integration.md#commands-menus-icons-and-styling); outside activation, a canvas action, tool change, lock, detach, or unload closes the complete surface. Lines, Dots, and Squares preview their actual repeating pattern; Squares uses one three-by-three grid with shared, square-cornered cell boundaries rather than separate rounded tiles. When the chosen background has guides, one full-width separator precedes a padded four-stop S/M/L/XL range control. On wide presentations the separator reaches both inner panel edges with no inline margin. On phones the choices and Spacing region use Obsidian menu typography, padding, surface, divider, group-gap, and touch-radius variables.

The overflow and selection context menus expose Bring forward, Send backward, Bring to front, and Send to back as four flat Arrange actions. Canvas context menus retain flat actions without submenus. Disabled boundary actions remain visible in the menu so their layer behavior is discoverable. These actions do not consume four permanent toolbar slots. Overflow also contains Settings and Keyboard shortcuts with the built-in `settings` and `keyboard` icons. On desktop and tablet both schedule opening an Inkbook dialog after the menu closes; on phones they open subpages of the existing sheet as specified in [Obsidian integration](obsidian-integration.md#commands-menus-icons-and-styling). Settings renders only the general settings content, while Keyboard shortcuts renders only its dedicated shortcut content; neither adds an internal view switcher.

### Document Save Status

Normal status labels and the saving spinner use the host's `--text-muted` color, matching adjacent native status-bar text. The saved check uses `--interactive-accent`; the failure icon and label retain `--text-error`.

The binding resolves its owning Markdown pane through public workspace leaves when the editor becomes ready, then compares stable pane-container identities on active-leaf events. Obsidian can temporarily detach retained editor DOM during mobile tab switches; this does not discard the authoritative model's ownership or save status. Actual editor detach, replacement, and disposal clear the binding. Repeated events and save-state updates do not rescan workspace leaves, measure layout, schedule frames, or observe host DOM.

Inkbook registers one lifecycle-owned item through `Plugin.addStatusBarItem()` in Obsidian's native status bar. Its owned item uses CSS ordering to appear at the left of the native items, without moving host DOM. It shows `Saved`, `Unsaved changes`, `Saving…`, or `Save failed` for the unlocked editor in the active Markdown pane; only the hover tooltip identifies Inkbook and its SVG path. A locked preview, another active pane, or no attached editor shows the muted text `No Inkbook embed open`. The host controls status-bar placement and platform visibility; Inkbook does not add an embed overlay or a mobile status-bar replacement. One workspace binding observes the authoritative document model, survives ordinary save and recovery transitions, and releases its subscription on editor replacement, lock, detach, or disposal. Public `active-leaf-change` events filter it through the active Markdown view's `containerEl`, without polling, document reads, scroll callbacks, or DOM measurements. `Saved` requires confirmation of the current document revision; completion of an older save leaves newer edits pending. This status does not add a timer or alter the existing 1,000-millisecond autosave debounce defined in [Rendering and Performance](rendering-and-performance.md#document-worker-autosave-and-export).

The item uses `role="status"`, polite announcements, and a descriptive tooltip; color alone never carries its meaning. `Saving…` includes a rotating progress icon and a static ellipsis, while `Saved` includes a check. `Unsaved changes` includes a static pencil in the same muted color as its text. `Save failed` includes a static circle with an exclamation mark. Each owned native icon uses a tight, predefined SVG viewBox around its glyph, including the two-unit stroke and rounded caps. Its intrinsic width follows that viewBox's aspect ratio, and its visible height follows the text's capital height (`1cap`, with a `0.75em` fallback). Supported engines trim the text box to the font's capital height and baseline; other engines retain centered line boxes. Icons and text share a centered layout without a vertical translation. Normalization happens only when the icon changes and requires no geometry measurement. All icons are decorative and excluded from accessibility announcements; the text remains authoritative. A status change crossfades the decorative glyph and label and animates their color while the live announcement and status semantics update immediately. The device's reduced-motion preference keeps the progress icon static, and its full-motion preference overrides the system preference. Failures retain the existing recovery actions and local session data. Only meaningful state changes update the item; repeated commits in the same state cause no DOM writes or icon injection. A path-only change updates the tooltip while retaining the icon. A dedicated lifecycle-owned React root renders this status content independently of editor-toolbar updates.

The owned content keeps its natural width rather than reserving a fixed status width. A React `motion.span` with `layout` owns position-and-size transitions for 120 milliseconds with the shared style-change easing, preserving its anchor as content width changes; Inkbook never sets or animates the native status bar's dimensions. Each keyed status surface is a direct `layout="position"` child with `layoutAnchor={false}`, preserving its visible right edge and neighbor spacing during crossfades without an intermediate projection wrapper. Motion retargets interrupted layout changes. Reduced motion applies layout changes immediately. The status owns no width observer, measured-endpoint controller, cubic-bezier sampler, frame loop, timer, or text-measurement probe; Motion owns measurement and interpolation. Disposal unmounts its React root and releases active layout and spinner animations.

Delete and Delete embed use the [shared derived danger tone](obsidian-integration.md#commands-menus-icons-and-styling) for both icon and text. Erase all is disabled when the canvas contains no elements and uses the native muted title instead of the caution color in that state. When enabled, it retains its confirmation and uses the `inkbook-eraser-caution` custom icon and owned title with the same orange caution color. Cut remains a normal action because it is clipboard-preserving and undoable. Copy, Cut, and Paste form the clipboard section, Delete has its own destructive selection boundary, Arrange actions form the next section, Copy embed is document-level, and Erase all plus Delete embed form the final destructive section. Separators appear only between those sections. Phone bottom spacing follows the shared sheet contract without changing host-wide safe-area tokens. Menu items use sentence case, expose their visible title as the accessible name, and retain visible disabled Arrange boundary actions.

The owned menu preserves arrow-key navigation and `Escape` dismissal. After it closes, focus returns to the control that opened it or to the canvas input surface. Mouse, touch, keyboard placement, target selection, and action availability are normative in [Features](features.md#canvas-context-menus).

Inkbook owns one shared operational-feedback presentation instead of using native Obsidian notices. Messages associated with a mounted drawing and messages without one share a fixed overlay in the owning document's body. Desktop and tablet place the column at the upper right, 32 pixels below the window's top edge and 10 pixels from its right edge. Phone places it at the upper center, with a top inset of `max(4px, var(--safe-area-inset-top))` and horizontal safe-area insets of at least 12 pixels. Placement matches the native Obsidian notice location without reading or mutating private host DOM. Independent lifecycle-owned anchors share the column without overlapping; phone uses reverse column order. Positioning is independent of drawing scroll, zoom, and Markdown pane geometry. Cards size to their content, capped at 36 rem and the available window width, without reserving empty action space. A minimum height of 64 pixels keeps messages with and without actions visually consistent. Text may wrap and increase card height without clipping, including unbroken words. In windows wider than 500 pixels, the status icon, text region, and complete action group remain in one horizontal row. At 500 pixels or below, the complete action group occupies its own full-width row with evenly distributed actions; the status icon and text stay together above it. Action hit targets remain 44 pixels square. These surfaces share the same background, border, spacing, status icon, concise title, optional explanatory detail, circular icon-only actions, and the toolbar's 220-millisecond scale entrance and reverse exit. Exit makes the surface inert and inaccessible immediately, while replacement, disposal, and plugin unload remove it without waiting. Settings validation remains directly below its field, the bounded worker fallback remains a once-per-window console warning, and unsaved detached data that requires a blocking decision retains the blocking recovery dialog.

Errors use `role="alert"`; warnings, information, and success use `role="status"`. Transient actionless feedback closes after five seconds. Recovery actions remain until the user resolves or dismisses the message, while the successful insertion Undo exception retains its documented five-second lifetime. A message replaces the current message at the same anchor instead of stacking, never steals focus, respects reduced motion and mobile safe-area insets, and mounts in the owning document for main-window and pop-out presentations. Every action has a tooltip and accessible name but no visible text label. The text region absorbs available width so the complete action group remains aligned to the trailing edge regardless of copy length. The shared action mapping uses `rotate-ccw` for Retry, `copy-plus` for Save copy, `pencil` for Continue editing, `x` for Keep preview or Dismiss, `refresh-cw` for Reload external version, `undo-2` for Undo, `trash-2` for Delete or Move to trash, and `settings` for Open settings.

Attached load and save failures preserve the last safe preview or active scene and place one persistent shared recovery surface at the shared window-level feedback position. Its title states the failed operation and its detail states which data remains safe. A load failure synchronously removes any delayed loading status before recovery mounts, so the two states cannot paint together; it offers Retry and Keep saved preview. An editor-interface startup failure uses the same attached recovery surface and does not also create a global message. A save failure performs the equivalent handoff from saving status to Retry, Save copy, and Continue editing. The detached-session recovery dialog uses the same feedback copy with visible text buttons: the primary Retry action, Reload external version, and Save copy. Retry is first in both DOM and visual order so native host focus starts on the non-destructive retry action. Its actions use the shared dialog layout and stack on narrow screens; the window-level feedback surfaces retain icon-only actions. Focus management follows the shared dialog contract below because no editor remains attached.

Saving uses an earlier feedback threshold than activation because input is already disabled while the write is pending. Input and uncommitted gestures are disabled immediately, the existing editor begins its normal lock transition immediately, and an icon-only `Saving drawing` status appears at the center of the embed's currently visible native-scroll intersection only when the latest required save is still unresolved after 150 milliseconds. It remains through coalesced successor saves, disappears on exact-revision confirmation, and is atomically replaced by attached recovery on failure. Retry starts a new delayed saving-status lifetime. Load and save failures show their recovery UI as soon as the failure is known rather than waiting for either feedback threshold. These statuses share the [fixed loading-feedback host](#loading-feedback), have no layout participation or pointer handling, expose `role="status"` with an accessible name, and retain a static progress icon when reduced motion disables rotation.

### Action dialogs

Confirmations, copied-embed paste choices, detached-session recovery, settings, and keyboard shortcuts use the public Obsidian `Modal` shell on desktop and tablet, where the host owns active-window placement, theme, dismissal, and focus containment. On phone, all of these dialogs reuse the shared adaptive bottom sheet defined in [Obsidian Integration](obsidian-integration.md#commands-menus-icons-and-styling). Dialog content uses a concise title, explanatory text, and named actions; destructive confirmation buttons use the host warning style. On desktop and tablet, action dialogs have a 440-pixel maximum preferred width; all action dialogs wrap long paths, and stack their 44-pixel-minimum actions on narrow screens. The native modal shell locally aligns the close-control block and inline insets through host spacing tokens; the title and content restore their inherited spacing values. Confirmation and choice dialogs request initial focus on Cancel (or Keep file); recovery requests Retry. Escape dismisses without confirming. Desktop and tablet retain the native close control; phone sheets have no close button and support the shared sheet swipe, outside activation, and Back handling.

After the Delete embed confirmations, the invoking presentation clips its current outer height to zero over the same 180-millisecond smoothstep as insertion, keeping its content at natural size and moving following Markdown continuously. Live Preview measures surrounding blank-line blocks included in the removal through the public CodeMirror layout API and progressively offsets their heights independently in the owned root start and end margins, so their final removal does not add a spacing jump. The disappearing presentation is inert. Markdown removal waits for the collapse; source identity and reference knowledge are revalidated afterward. Live Preview maps the current CodeMirror scroll snapshot through the Obsidian Editor text mutation, preserving the visible note position without revealing an offscreen Markdown cursor. Cancellation, stale identity, or failure before removal restores the presentation, while disposal cancels outstanding frames. Reduced motion skips interpolation. Direct edits to host-owned Markdown retain the host deletion behavior.

Delete embed retains separate embed and optional last-reference SVG-trash confirmations. Dismissing the second keeps the file while completing the already-confirmed embed removal. Source identity and reference knowledge are checked again after the asynchronous decisions. Erase all cancels on detachment or disabling and rejects a changed document revision. Copied-embed paste explains each choice in the dialog body and presents Insert reference and Create copy as standard text buttons, with consequences linked through accessible descriptions. Pending dialogs must not authorize stale mutations after their owning operation ends.

## Toolbar Design

All primary controls share one continuous toolbar surface. Copy, Cut, Paste, and Delete intentionally use separate circular surfaces outside that primary pill. A previously available Paste control remains visually unchanged while another Clipboard operation runs, so Copy does not replay Paste presence motion or dim its surface.

The primary toolbar is one 48-pixel-high rounded surface with 2 pixels of internal padding, the host menu background, a 1-pixel host menu border, and a restrained host shadow. The toolbar and separate circular context controls use `--menu-background` and `--menu-border-color`. The locked preview and active background containers retain the portable page-surface colors `#F6F6F6` in light mode and `#212121` in dark mode. The persistent outer embed shell owns one restrained shadow in locked and active states; the inner locked button explicitly suppresses native host button shadows and never changes depth on hover. Every 44-pixel primary control and its hover, active, and focus treatment are circular, with a consistent 2-pixel gap across the complete track. The complete primary pill scales from zero to full size over 220 milliseconds when the editor opens and applies the exact reverse while it closes. Its individual buttons and active-tool indicator do not run separate entrance or exit animations. Saving starts immediately while the presentation remains attached long enough to finish this decorative exit. Each conditional context action is a 48-pixel circular surface with exactly the same resolved background color, border, shadow, and top edge as the primary toolbar and an 8-pixel gap from adjacent surfaces; its transparent positioning group contributes no visible backdrop. The visual order is Paste, Copy, Cut, Delete. These controls use the same zero-to-full scale motion and its exact reverse. When several appear because selection or clipboard availability changes, their fully opaque, fixed-size surfaces start from left to right with a 50-millisecond stagger. When several disappear, the same sequence runs from right to left. Every disappearing surface retains its fixed layout slot until the last staggered exit in that batch reaches zero scale; all completed exit slots are then removed atomically, so no exiting control changes its layout origin while another exit remains visible. If the atomic removal or insertion changes a remaining control's X position, that control translates from its previous visual position to its new layout position over 120 milliseconds instead of jumping. A complete editor lock scales every still-visible context control out concurrently with the primary pill so every toolbar exit completes within 220 milliseconds; presentation teardown also waits for the concurrent 240-millisecond lock layout transition. Entrance timelines remain paused while the editor chrome is hidden for initial scene preparation and begin when the active scene becomes visible. The motion never animates width or resizes a 44-pixel primary control. A successful Copy, Cut, or Paste from the toolbar, keyboard, or canvas context menu remounts the matching context icon's 900-millisecond confirmation sequence: the action glyph scales and rotates into `check`, remains legible, then returns to its original glyph without replacing the button or changing layout. Repeating the action restarts that sequence. Reduced motion holds the check for the same bounded confirmation lifetime and switches glyphs without interpolation. Active tools keep normal icon geometry above one persistent accent-tinted circular indicator. A tool change translates that indicator between the old and new tool over 120 milliseconds, so the accent surface visibly slides without replacing either button or icon. The Finger Drawing toggle retains its local pressed treatment because it is a mode toggle rather than the active drawing tool. Destructive Delete uses the host error color. Every control is keyboard-focusable and shows a visible ring during explicit keyboard navigation. Reduced motion moves the pill, the indicator, conditional controls, and context-layout changes directly to their final states.

Every control has a 44-by-44-pixel hit target. The icon may be visually smaller and does not change size between rest, hover, active, and focus states. Controls retain accessible names through `aria-label` and use Obsidian's hover tooltips without duplicate browser `title` tooltips.

The canvas input surface has an accessible name through `aria-labelledby` referencing its own hidden text label. It has no hover tooltip and does not carry `aria-label` or `title`, because Obsidian interprets `aria-label` as a tooltip trigger. Toolbar tooltips use the host's pointer-type filtering and touch cancellation; Inkbook does not introduce a separate touch or long-press tooltip trigger. An author description in `!inkbook[Diagram description](drawing.svg)` or the Wiki alias `!inkbook[[drawing.svg|Diagram description]]` names the locked Edit handwriting button and describes the active canvas through a lifecycle-owned `aria-describedby` target. Descriptions are trimmed text, assigned with `textContent`, never interpreted as HTML or inferred from the drawing. Missing descriptions retain the generic preview name. Equal-length description-only edits within the same Live Preview embed update its text and accessibility relationships in place without opening a new editor session. The canvas additionally owns concise hidden keyboard instructions and polite operation status under the [keyboard navigation contract](keyboard-shortcuts.md#canvas-object-navigation-and-geometry-editing); scene culling never removes these descriptions or creates individual focusable ink nodes.

The 48-pixel toolbar track is positioned inside a 68-pixel overlay envelope with 8 pixels above and 12 pixels below it. The complete envelope is translated above a zero-height host, so it creates no dead page padding, moves no surrounding Markdown, and removes no writable SVG space.

It is positioned above the drawing area inside the same in-place editor boundary while painting over the note rather than participating in note flow. The zero-height host uses native sticky positioning. Its inset compensates for the measured top padding of the already resolved public scroll owner, without private Obsidian selectors or per-scroll JavaScript writes. As the note scrolls, the toolbar moves normally until it reaches the visible top edge, remains there while its embed is visible, and leaves the viewport with the embed's bottom boundary.

## Responsive Behavior

The primary toolbar has two layout stages, selected by whether the measured primary control track plus its fixed 136-pixel side corridor fits the available width:

1. Wide: use this stage when the complete track and corridor fit. The track remains centered.
2. Scrollable: use this stage when the primary track plus its fixed side corridor do not fit. Buttons and gaps remain unchanged. One transparent 50-pixel-high capsule-clipped horizontal scrollport contains the complete primary pill followed by every separate 48-pixel context-action circle, with one transparent pixel above and below the control surfaces so their outlines remain intact. Partially visible surfaces retain rounded scroll edges instead of a rectangular cut. The toolbar shadow belongs to the outer, non-scrolling composition and therefore remains visible beyond the clipped scrollport without forming a rectangular backdrop. The scrollport hides only its own horizontal scrollbar and applies no edge fade or alpha mask. It never affects the native vertical Obsidian scrollbar.

The buttons are never reduced in size and never overlap. Context-action visibility, handedness-selected corridor placement, and independent scrolling follow the [toolbar context-action contract above](#toolbar-layout). Wide uses equal flexible grid corridors around the intrinsic primary pill; context placement follows its actual edge without a measured half-width or an additional React resize observer. Motion projects the visible pill and its neighboring controls together when membership or layout stage changes. The owner-window layout observer still refreshes primary-track overflow whenever its actual size changes, including resizes that remain within the same responsive stage. Local pointer and keyboard press feedback stays inside the non-projecting button surface; roving focus updates tab stops without rerendering the layout tree.

The pre-measurement state is Wide. The editor keeps the chrome hidden during its initial stable-width measurement, resolves the actual stage from the mounted control track, and reveals only that measured result. After initialization, the editor accepts every changed positive container width in the next coalesced frame. It observes the mounted primary toolbar directly as well as chrome mutations, so Wide or Scrollable stage, measured primary-pill edge, and context-action placement converge from the same current geometry during and after a window resize. A resize MUST NOT be required to correct first-open geometry.

The left-handed setting mirrors the context controls to the left of the centered primary toolbar while retaining Paste as the control nearest the primary pill. Changing handedness animates the complete context group and each reordered control from its previous visual position over 120 milliseconds. The mirrored context-presence stagger runs from the primary pill outward, and the complete row retains the same fit calculation. In Scrollable, the mirrored context group precedes the primary pill inside the same horizontal scrollport.

Toolbar, selection, container-height, adaptive-panel, modal, feedback, and preview transitions follow [Quality, Performance, Animation, and Testing](quality-and-testing.md). Obsidian retains motion ownership of its Markdown editor menu. Inkbook owns its canvas and toolbar menu, adaptive-panel, and wide-modal motion; phone dialogs share adaptive-panel motion. Reduced motion preserves every owned final state without interpolation.

## Menus and Adaptive Panels

Overflow, Shape Picker, canvas context actions, Style, and Background use the shared Inkbook-owned adaptive surface. Menu actions preserve the host menu appearance, ordering, grouping, icons, checked and disabled states, and keyboard behavior. Active Shape is a drawing-tool control and never doubles as the picker trigger.

The following rules apply:

- Only one owned menu or adaptive panel is open per presentation.
- A click or drawing action on the canvas, tool change, lock, detach, or unload closes the active surface.
- Pressing an open toolbar menu's own trigger toggles it closed on click. Its pointer-down event is not an outside dismissal, including a hold longer than the exit animation and reduced-motion operation.
- Menu styling remains scoped to owned DOM and uses host theme tokens. Inkbook never traverses private host DOM or changes global safe-area tokens. The native Markdown editor insertion menu remains host-owned.
- On wide non-phone presentations the adaptive panel uses the host-native visible trigger gap, four pixels on desktop and two pixels on tablet, clamps inside the owning viewport, flips above when required, and closes on outside activation or Escape. Desktop and tablet surfaces use the shared fast opening and closing animations; action activation, handoff, and owner disposal remove them immediately. Content changes never replay that entrance. Tablets additionally use the native translucent mobile menu background and backdrop-filter tokens.
- A wide panel content change measures and applies its updated placement in the same Motion layout commit. If the new height requires flipping above the trigger, the panel follows that placement change without a viewport-position jump. Both projection nodes share the same transition configuration. A zero-duration render applies final geometry through static transform styles and Motion's public `transformTemplate`, retaining the existing controls and focus. Motion 14.6 has no public per-component layout-projection finish API; its existing clock may drain without visible movement. Returning to Full alone does not reveal it. The next Full content change measures the visible end layout before resuming interpolation, without global resets, manual geometry, or animation timers. Phone subpage opacity and translation animations are canceled separately through their existing lifecycle.
- On phones the same adaptive panel becomes a bottom sheet bounded by the host safe-area insets. It has no border, uses the native top radius, backdrop, 15-percent grabber, host menu padding, hidden internal scrollbar, the keyboard-aware height limit defined in [Obsidian integration](obsidian-integration.md), keyboard-aware absolute positioning, whole-surface downward-swipe dismissal, and Android Back handling through the public Obsidian Modal lifecycle. A claimed downward gesture follows the finger and fades the backdrop. Releasing below the distance and velocity thresholds animates the sheet back instead of closing it; reversing to the origin also suppresses the trailing control click. The entrance is a separate one-shot presence state and never replays after this return animation. Direction arbitration preserves taps, horizontal controls, upward scrolling, and bidirectional scrolling while content is away from its top. The handle remains available at every scroll position. Phone sheets use one surface transition without section staggering.
- Every standard menu entry and non-interactive group label has an icon. Checked choices expose their selected state immediately; Background choice checkmarks fade in or out with Motion and are disposed when their controls leave the panel. Actual deletion uses the shared derived danger tone, and content clearing uses the distinct derived orange caution tone.
- Shape entries are ordered as line tools, geometric shapes, and structures, with native separators but no redundant group headings. The active arrow glyph independently represents all five start and end nodes: None, Arrow, Triangle, Diamond, and Circle. The coordinate-system glyph represents either two or three axes according to its 2D or 3D default. The table glyph shows only its internal header divider and central two-column divider, without an outer frame.
- Style has no redundant heading. Selection controls follow the [demand-driven chrome contract](rendering-and-performance.md#imperative-scene-ownership). Wide panels use compact 36-pixel controls in flat sections separated by native dividers. Phone panels use native gray subsection surfaces and retain 44-pixel touch targets. Both variants retain host-theme focus rings, labelled color swatches, five evenly sized XS-through-XL choices, dash and endpoint previews, a Pressure sensitivity switch in the same row as its label, a column stepper with a directly editable numeric field (whole columns, clamped to 1 through 12, committed on Enter or focus loss), and full-width sliders with compact value fields. The switch's initial paint is written before activation can change its native checked rendering; later toggles animate track and thumb feedback without delaying the checked state. A visible unit remains inside the centered field but outside the editable number. Slider and number input update each other live and commit one style change on `change`.
- Background changes remain inside the same panel. Showing or hiding Spacing animates only the panel's block size, without replaying the standard open animation. Back performs a focus-preserving handoff to the Overflow menu before the next paint.
- The panel traps focus while open, labels graphical controls for assistive technology, and returns focus without scrolling to the trigger or canvas when the final surface closes.

Menus and adaptive panels use the document and window that own the embed. Static custom control styling is limited to the owned adaptive-panel subtree and uses Obsidian CSS variables without private host DOM fields or selectors. The concrete host API and pop-out requirements are defined in [Obsidian Integration](obsidian-integration.md).
