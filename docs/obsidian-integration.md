# Obsidian Integration

## Authority and Support Surface

This document defines the host boundary for Inkbook. Domain, editor, rendering, and persistence code MUST depend on narrow adapters and MUST NOT import undocumented Obsidian internals. The settings-owned hotkey-conflict gateway below is the only permitted private host read.

Inkbook supports Obsidian desktop, iOS, and Android with `minAppVersion: "1.13.0"` and `isDesktopOnly: false`. Runtime code uses documented Obsidian APIs and browser APIs except for one isolated read-only effective-hotkey gateway. Node.js, Electron, `FileSystemAdapter`, `Vault.adapter`, the global `app` object, private workspace fields outside that gateway, private host CSS selectors, and host-DOM traversal are forbidden.

The hotkey-conflict gateway may read only `app.hotkeyManager.defaultKeys` and `app.hotkeyManager.customKeys` through a narrow local type and runtime validation. It combines them using host precedence, where any custom command entry replaces its defaults, and never writes manager state, opens host settings, traverses host DOM, or exposes the manager to another module. Missing or malformed private state disables only host-conflict detection. Inkbook-local and fixed-binding validation remains active. This exception exists because the public Obsidian API exposes command defaults but not the complete current customized binding map. Replace the gateway and remove this exception as soon as a public effective-hotkey API is available.

The required host behavior is:

| Obsidian mode | Inkbook behavior                                                                  | Public integration                                                                         |
| ------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Reading view  | Replace a safely recognized standalone Inkbook block with an owned preview widget | `Plugin.registerMarkdownPostProcessor()`                                                   |
| Live Preview  | Replace recognized Inkbook embeds with full-width block widgets                   | `Plugin.registerEditorExtension()` with a CM6 `StateField`, `ViewPlugin`, and `WidgetType` |
| Source mode   | Preserve editable Markdown source; do not replace the embed text                  | Obsidian `Editor` for user-initiated text changes                                          |

Inkbook uses an explicit custom Markdown contract: `!inkbook[[path.svg]]` for a generated Wiki link or `!inkbook[label](path.svg)` when Obsidian generates Markdown links. The `!inkbook` prefix is not native image syntax. Obsidian therefore creates no SVG image host, native SVG controls, or image-resizer target for an Inkbook block. The inner link remains a normal host-generated link so Obsidian can resolve and track the attachment path.

The Reading-view postprocessor resolves a candidate through `MarkdownPostProcessorContext.sourcePath` and the section returned by `getSectionInfo()` immediately before use. The returned `text` is the full Markdown source; the validated inclusive `lineStart`/`lineEnd` bounds identify the rendered section within it. It excludes code and preformatted descendants, parses candidates against the complete source to preserve code/comment exclusion, and requires only the trimmed bounded section to consist of exactly one recognized custom embed. Reading-view action references retain that source identity and the embed offsets within it. While recognition is pending, a lifecycle-owned neutral loading placeholder replaces the custom link as specified in [Embed UI](embed-ui.md#first-appearance). Before SVG ownership, bounded lazy classification through `Vault.cachedRead()` requires the canonical root-level `data-inkbook-format="inkbook"` marker and canonical root `viewBox`; the retained classification contains the safe preview, aspect ratio, persisted revision, and SHA-256 output hash. The postprocessor repeats its section and resolved-document correlation after asynchronous classification and accepts the result only while the cache still exposes the same revision and hash, then replaces only the rendered section host's contents with one lifecycle-owned block root. The supplied host itself remains owned by Obsidian, including when postprocessing occurs before that host is attached. A mounted child subscribes to later recognition changes, replaces its preview and attachment identity only from the latest terminal classification, and restores the original child nodes if the target becomes invalid. Unload restores those same child nodes without replacing the host. If section information is `null`, the section contains other content, the target cannot be resolved unambiguously, or document classification fails, Inkbook leaves the rendered custom link unchanged and does not unlock it.

Live Preview starts recognition only for visible custom blocks while `editorLivePreviewField` is active. Its state field retains bounded, resolved embed candidates and their decorations so pending placeholders exist before the first paint. Initial discovery and structurally relevant Markdown edits parse the complete bounded source to preserve code, comment, and standalone-block exclusion. Single-line alphanumeric edits that preserve unindented ASCII prose map existing positions and entrance state instead of repeating discovery. This fast path requires at most 2 Mi UTF-16 code units, conservatively below the 8 MiB UTF-8 input limit; other edits use complete bounded discovery. Recognition results update only matching candidates without reparsing Markdown or resolving unrelated links. Each view coalesces a burst of recognition notifications into one lifecycle-owned microtask and ignores unrelated document IDs. Disposal prevents a queued update from dispatching. The cache and scheduling limits below apply equally to Reading view and Live Preview.

Recognition runs at most four reads concurrently and queues at most 4,096 additional distinct requests. Requests for the same file signature share one promise. Before layout readiness, requests remain queued without reading. Queue overflow returns a temporary unsuccessful result without caching an invalid classification; an existing safe preview remains usable and a new unresolved reference follows the normal Markdown fallback. Live Preview suppresses another attempt for that reference until a document edit or context change, avoiding an immediate retry loop. Invalidation and disposal settle pending callers, discard stale results, and retain active read slots until the underlying reads actually finish. A failing subscriber cannot block other subscribers or the queue.

Completed classifications use a separate least-recently-used cache limited to 256 entries and 32 Mi UTF-16 code units of SVG markup. Budgets are enforced on every completion using incremental accounting; a single oversized valid preview may remain as the only entry. Creation and modification invalidate the relevant path, and each result is correlated with the file signature, validated persisted revision, and SHA-256 output hash.

Recognized block replacements are stored in a highest-precedence CM6 `StateField` and provided directly through `EditorView.decorations.from(field)`. They MUST NOT be returned through a `ViewPlugin` decoration function because CodeMirror rejects layout-changing block decorations from dynamic plugin sources. The companion `ViewPlugin` owns visible-range discovery, asynchronous recognition subscription, and viewport refresh only. The state field updates on document, mode, source-file, or terminal recognition changes and makes each replacement an atomic range. If vault invalidation makes an already recognized target temporarily unknown, the existing decoration and widget remain authoritative while one coalesced reclassification is pending; only a terminal negative result may remove them. The resulting block widget occupies the complete note content width. Root size changes normally request one coalesced CodeMirror measurement. During a lock, unlock, growth, or shrink transition, Inkbook defers those host measurements and requests exactly one after the transition, so CodeMirror does not repeatedly re-anchor the note while the block height changes. Unlock preserves the current block root, width, top-edge anchor, and attachment, mounts the scene inside that root, then animates its block size from locked to the active page. A zero-height native-sticky host bounds the toolbar to that active editor while an absolute overlay lifts the toolbar above the page without contributing block height or moving adjacent Markdown. Its inset compensates for the resolved scroll owner's measured top padding and requires neither private host selectors nor per-scroll JavaScript. The complete locked-preview button is the handoff node and is removed only after the active scene is ready, so no empty host-height button can remain as a duplicate bar. A stroke commit, autosave, resource refresh, or theme update MUST NOT detach or recreate the active widget. Escaped syntax, inline or fenced code, HTML comments, incomplete trees, native SVG embeds, and ordinary links fail closed. Widget equality includes the resolved document path, resource URL, and validated content identity, so a same-path content change cannot retain stale preview DOM. The presentation attachment carries that same identity into the unlock operation. After complete file and worker validation but before Store adoption, the session requires the loaded revision and output hash to equal the preview identity. A mismatch terminates the candidate runtime, publishes no model, refreshes the preview from the newly validated persisted identity, and exposes version-change recovery. Markdown text mutations MUST use the Obsidian `Editor` API, such as `Editor.replaceRange()`, so cursor, selection, folds, history, and mobile behavior remain host-managed.

Inkbook does not intercept `![[file.svg]]` or `![label](file.svg)`. Those remain ordinary Obsidian image embeds and other image plugins may handle them normally. Only the explicit `!inkbook` prefix creates an Inkbook presentation. Recognition first performs an incremental complete safe-envelope inspection with the same strict element, attribute, class, stylesheet, path, URL, and byte allowlists used by the file contract. It then parses the proven-safe source with the owning window, removes metadata and the standalone stylesheet, and imports only the inert presentation SVG into a plugin-owned surface. Scoped host CSS supplies the canonical light/dark palette and one-screen-pixel guide stroke, so the locked grid matches the active scene at fractional width fit. The surface spans the complete stabilized content width, derives its height from the canonical SVG aspect ratio, has no pointer target, and remains inside an owning activation button that prevents and stops the activation click. The button explicitly relinquishes Obsidian's generic fixed button height so its block size follows the SVG aspect ratio and the aligned empty-page minimum. Native SVG controls and image-resizer overlays cannot attach because the Markdown never creates a native image element or native embed. Inkbook owns interaction inside its scoped root; external image tools MUST NOT be treated as part of the Inkbook lifecycle or editor state.

## Widget and Resource Ownership

Each Reading-view embed with listeners or UI owns one `MarkdownRenderChild`, registered through `MarkdownPostProcessorContext.addChild()`. Each Live Preview embed owns one `WidgetType` instance. Both attach the same editor session facade but own their presentation resources independently. One plugin-scoped `WorkspaceEditorCoordinator` is shared by the main window and every pop-out belonging to the same `App.workspace`.

Every widget unload path MUST immediately:

- cancel animation frames, UI timeouts, and pointer gestures, reverting uncommitted previews
- release pointer capture and remove document-level input listeners
- disconnect `ResizeObserver` and other observers
- revoke owned Blob URLs
- close every presentation-owned menu session and remove owned menu-control DOM
- detach the canvas input surface and its context-menu, keyboard, wheel, and pointer handlers
- release its reference-counted native-scrollbar stability lease
- unmount the React root
- invalidate the widget-attachment generation so late UI work cannot mutate detached state

The widget then asks the coordinator to detach its session. A clean session terminates its worker and releases all state. A dirty or saving session keeps its worker epoch, active save, prepared successor, and export generation under the single detached-save lease defined in [Workspace Activation and Detachment](specification.md#workspace-activation-and-detachment); widget unload MUST NOT cancel that save. The lease owns no DOM, `Document`, `Window`, leaf, view, widget, React root, menu, observer, or input listener.

Plugin-wide host events use `registerEvent()`, persistent DOM listeners use `registerDomEvent()`, intervals use `registerInterval()`, and other cleanup uses `Component.register()`. Widget resources belong to the widget component rather than a global collection. The plugin main object MUST NOT retain leaves, views, widgets, React roots, or clean editor sessions after their component unloads. The coordinator may retain only the single dirty detached or headless recovery session until it reaches a confirmed terminal outcome.

Pop-out windows are supported. DOM creation, menus, animation frames, and event registration use the owning embed's `ownerDocument` and `defaultView`, or Obsidian's `activeDocument` and `activeWindow` when no embed exists. They MUST NOT assume the main global `document` or `window`.

The production build emits a small synchronous Obsidian plugin entry and embeds the complete minified activation runtime as gzip-compressed, Base91-encoded bytes in `main.js`. That runtime contains separately compressed document-worker and React 18 editor-chrome modules. Loading uses only the owning window's standard `Blob`, `URL`, `Response`, and `DecompressionStream` APIs plus native dynamic `import()`; it performs no network request and creates no additional release artifact. The build permits only `obsidian`, `@codemirror/language`, `@codemirror/state`, and `@codemirror/view` as runtime host modules and fails if the generated runtime requires any other external module. One activation-runtime promise is shared per owning window, failed loads remain retryable, and temporary host-module exposure plus the Blob URL are removed when import settles. Plugin activation generations prevent a runtime or settings result from registering anything after unload or an intervening reload.

The nested editor-chrome module still has one load promise per owning window, while each presentation owns a distinct React root. Its Blob URL is revoked when module import settles, the final consumer cancels, or the five-second load bound expires. A detached presentation cancels its pending mount, retains only the latest coarse props while loading, and cannot mount after unload. Input, toolbar-dependent layout, and static-preview handoff remain disabled until the React root has mounted and the toolbar has been measured. A missing compression API, CSP rejection of an owned `blob:` module, decode error, import error, or timeout preserves the plugin-owned locked preview and creates no React root. This keeps React out of the initial execution and render paths while retaining a progressive fallback when a supported Web API or `blob:` module policy is unavailable.

Activation requests from all owning documents pass through the same coordinator and identify the normalized SVG document separately from the widget attachment and its generation. The coordinator contains no DOM reference. Its workspace tokens, one pending-request slot, and detached-save lease make rapid cross-window activation deterministic. Widget unload cancels a matching pending request before releasing resources. A recovery modal resolves its presentation document only when shown and never stores that window after close.

`onload()` first loads the owned activation runtime, then that runtime performs only settings loading and registration of commands, the settings tab, the postprocessor, and the editor extension. It performs no vault scan, SVG parse, React mount, or worker creation. The presentation hooks register before `workspace.onLayoutReady()` so restored notes receive their neutral placeholder before their first paint. A specific visible custom block may queue recognition before layout is ready, but vault reads and safe-preview parsing wait for that callback. Unload releases pending recognition without starting a read. Layout-dependent work and vault `create` listeners begin inside `workspace.onLayoutReady()`. Plugin unload invalidates the activation generation, cancels work, and rejects late runtime or settings results; it MUST NOT depend on an awaited asynchronous `onunload()`. Lock still awaits its save. Best-effort shutdown work MAY be registered with the workspace quit task mechanism.

## Native Scroll Owner and Scrollbar Stability

Inkbook never creates or owns a vertical scroll container. The presentation adapter resolves the nearest Obsidian scroll owner through the computed-overflow ancestor algorithm in [Zoom Functionality](zoom.md#anchored-zoom), using only the embed's `ownerDocument` and `defaultView`. It does not query a private Obsidian class or assume a main-window DOM shape.

After the public integration safely recognizes an Inkbook presentation and before Inkbook performs its first positive-width preview or editor measurement, that presentation acquires a reference-counted lease for the exact scroll element. Initial class acquisition is a write-only phase; Inkbook reads post-style width in the following animation frame and enables no editor input before that measurement settles. The lease applies one public Inkbook marker class that requests `scrollbar-gutter: stable` and `overflow-y: scroll` for the full recognized-presentation lifetime, including lock and unlock. This reserves the right-hand native scrollbar gutter before width-fit zoom and prevents activation or pen contact from changing the content width. Multiple Inkbook presentations that resolve to the same element share one count; the class is removed only after the last lease is released. The owning-document lease registry deletes its element entry at count zero and is not retained by the workspace coordinator or a detached-save lease. An unrecognized candidate acquires no lease and leaves the custom link unchanged.

A live presentation whose scroll owner changes because of a workspace layout move performs a two-frame transfer. In the first frame it reads and resolves the candidate before any write, then acquires the new lease in the write phase while retaining the old lease. In the next animation frame it reads the post-style embed and owner geometry, applies the new measurement in the write phase, and only then releases the old lease. A real Widget or `MarkdownRenderChild` unload with no live presentation successor releases its lease immediately; a later remount acquires a fresh lease and never inherits a DOM reference through the coordinator. Target invalidation and plugin unload also release immediately.

The marker MUST NOT use `::-webkit-scrollbar`, `scrollbar-width`, synthetic scrollbars, fixed scrollbar widths, or theme-specific colors. It MUST NOT apply `overflow: hidden`, replace the owner, add a nested vertical scroller, or toggle any overflow or scrollbar property from a pointer handler. Its removal restores the host cascade rather than writing guessed prior values. The horizontally scrollable toolbar remains independent and may hide only its own horizontal scrollbar.

Inkbook measures `containerWidth` from the positive content-box width of its own background container after the lease applies, never from the scroll owner's full `clientWidth`. The embed root uses `box-sizing: border-box` and `max-inline-size: 100%`. A read phase additionally compares the background container's right edge with the scroll owner's client right edge, calculated from the owner border box, `clientLeft`, and `clientWidth`. If nested padding, readable-line width, a list, a callout, or another host layout would place the embed past that edge, the next write phase clamps the root to the non-negative remaining inline size and schedules a new measurement frame before input is enabled. The canvas input surface uses `inset: 0` within the final background container. It never adopts the pane width and cannot cover the native scrollbar gutter.

On desktop systems that expose non-overlay native scrollbars, the right-hand scrollbar track MUST remain present before, during, and after a pen gesture. Operating systems and mobile WebViews may render native scrollbars as auto-hiding overlays even with `overflow-y: scroll`; no public Obsidian or browser contract can force that native overlay thumb to remain painted. CSS reserves `scrollbar-gutter: stable` space for classic scrollbars, while native overlay scrollbars consume no gutter by definition and therefore do not change `clientWidth` when painted or hidden. Inkbook never causes the hide and produces no width or position shift in either mode. Replacing the native control with a custom scrollbar is out of scope.

Pointer capture, the pen scroll guard, note scrolling, anchored zoom, and layout compensation remain main-thread presentation work. No scroll owner, `Document`, `Window`, DOM reference, pointer event, layout measurement, or camera update crosses the document-worker boundary.

During every Inkbook-owned block-height transition, the presentation temporarily disables browser scroll anchoring only on the resolved Obsidian scroll owner and retains the embed root's viewport Y position through the transition plus two settlement frames. Unlock acquires this hold before inserting or measuring any editor DOM, so bottom-pinned notes cannot move during hidden scene preparation. Nested or immediately retargeted transitions share the reference-counted hold. The hold performs one constant-time root-position read per frame and writes `scrollTop` only after measured host drift; a host scroll event receives the same correction synchronously so no intermediate bottom-pinned position reaches paint. Height-only frames never rewrite camera state, and CodeMirror receives one deferred measurement after the transition marker clears. Wheel, vertical touch movement, or a vertical scroll key transfers control to the user and rebases the retained visual position instead of fighting the gesture. The hold follows a transferred scroll owner and is always released on disposal.

On touch devices, pending and vertically resolved canvas contacts remain available to the browser's native Obsidian note scroller. Inkbook contains a contact at its input boundary only after horizontal page pan, pinch, enabled finger drawing, or an eligible preselected-annotation drag wins arbitration, so host pane and side-panel gestures cannot latch an Inkbook-owned contact. The claimed non-passive touch stream is cancelled from `touchstart` onward to prevent browser scrolling from taking over a drag that began inside a selected box or group overlay, or within the touch hit tolerance of a selected line or arrow centerline. Unclaimed contacts are never cancelled. Pen pointer down, move, up, and cancel events are instead owned and cancelled at the canvas capture boundary for their complete lifetime, preventing Obsidian note scroll and drawer swipe handlers from claiming drawing input. Touch-down on an unselected annotation is neutral and neither selects nor moves it; only a confirmed short tap selects. Pointer-up, pointer-cancel, touch-end, and touch-cancel are not hidden from host cleanup. Inkbook checks for a stale captured touch in the next event-loop task after terminal dispatch, never between listeners of the same terminal event. It also releases stale state before a reused primary pointer starts, on window blur, and when the owning document becomes hidden. A normal second pointer used for pinch is not mistaken for a stale primary contact.

## Vault, File, and Link APIs

All paths are untrusted. Inkbook rejects absolute paths and traversal segments before passing a vault-relative path through `normalizePath()`.

Supported operations are:

| Operation                    | Required API and rule                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Resolve a known path         | `Vault.getFileByPath()` or `Vault.getFolderByPath()`, followed by a concrete `TFile` or `TFolder` check             |
| Read for display             | `Vault.cachedRead()`                                                                                                |
| Read for editor unlock       | Size preflight through `TFile.stat.size`, then `Vault.readBinary()` and transferable worker validation              |
| Save an existing SVG         | Size-preflighted, worker-validated `Vault.read()` followed by `Vault.process()` with a synchronous exact-base check |
| Create an SVG                | `Vault.create()` after collision-safe path resolution                                                               |
| Resolve attachment placement | `FileManager.getAvailablePathForAttachment(filename, sourcePath)`                                                   |
| Generate Markdown link text  | `FileManager.generateMarkdownLink(file, sourcePath)`, prefixed with `!` for an embed                                |
| Resolve a link target        | `MetadataCache.getFirstLinkpathDest(linkpath, sourcePath)`                                                          |
| Determine references         | `MetadataCache.resolvedLinks` only after metadata resolution; uncertainty denies deletion                           |
| Rename a managed file        | `FileManager.renameFile()`                                                                                          |
| Delete recoverably           | `FileManager.trashFile()`                                                                                           |

The complete SVG is generated and validated before `Vault.process()` starts. Immediately before every uncached full-file read used for expected-base preflight, mandatory post-write read-back, verification retry, or external-change verification, the bounded persistence port resolves the current `TFile`, records its object identity plus `{ path, ctime, mtime, size }`, and rejects a known size above the 64 MiB file limit. Reads and `Vault.process()` calls for the same normalized path are serialized. After the host read, the port resolves the file again, requires the same identity and metadata, and checks the actual UTF-8 byte length before worker dispatch or adoption. A mismatch, replacement, growth, disappearance, over-limit result, or indeterminate value fails closed and preserves dirty or verification-required state.

Obsidian 1.13 exposes only full-materialization `Vault.read()`, `cachedRead()`, `readBinary()`, and `process()` operations. It has no public range, stream, abort, or `maxBytes` read. The preflight therefore prevents a known oversized file from being read and the postflight prevents raced bytes from being accepted, but external growth between metadata inspection and the host read can still be materialized transiently by Obsidian before Inkbook rejects it. Inkbook MUST NOT bypass this mobile-compatible boundary through `Vault.adapter`, Node, Electron, `FileSystemAdapter`, or undocumented APIs. This residual host-API limitation is recorded rather than hidden behind a false hard-memory claim.

A permitted preflight `Vault.read()` is hashed and revision-checked in the document worker against the last confirmed base. Normal preflight and read-back carry the active save's same `saveOperationId` and target revision and do not advance `exportGeneration`; stale identities are rejected before adoption. If the executor fails after writing begins, read-back instead uses the new executor epoch and a new `verificationOperationId` bound to the immutable old save ID, revision, and output hash. The exact preflight string is retained only until the synchronous `Vault.process()` callback compares the callback's current content with it. This catches an external change in the preflight-to-process race; a mismatch throws a structured conflict and writes nothing. The callback also scans at most 4 KiB for the canonical `data-inkbook-revision` and compares the prepared result revision with the editor's current revision immediately before returning output. It performs no XML or JSON parsing, hashing, serialization, asynchronous work, or allocation proportional to element count. Exact string comparison counts toward the autosave main-thread budget. A successful callback returns the already generated complete SVG and releases the preflight string.

Every vault-modification notification remains untrusted and is verified through the same bounded persistence boundary. Coalesced host notifications are never suppressed by document path alone: after the notification batch settles, Inkbook validates the stable current file and compares its persisted revision plus SHA-256 output hash with exact read-back confirmations. Only an exact identity match may suppress the batch; a different, unreadable, replaced, or raced identity enters normal external-change verification. Verified output equal to either the last confirmed base or the currently active save proof is classified as unchanged regardless of notification order or a newer dirty in-memory revision. Such a notification MUST NOT reload, lock, detach, or place the active editor into recovery. Only verified output with a different identity may enter the external-change conflict path. Suppressing a known host event is an optional optimization and never the correctness boundary.

Active Markdown changes, including embed insertion, removal, duplication, and insertion undo, use the current `Editor`. Background Markdown changes use `Vault.process()`. CodeMirror extensions detect targets and manage widgets but do not bypass the `Editor` for document text changes.

Inkbook's Markdown embed discovery accepts at most 8 MiB of actual UTF-8 input and returns at most 4,096 recognized custom Inkbook matches per document pass. Exceeding either limit yields no Inkbook targets and performs no Markdown or presentation mutation; it does not fall back to an unbounded second parse.

Reference checks MUST NOT scan or parse every Markdown file. Direct path lookup, metadata-cache link resolution, and the existing data-preserving uncertainty rule are mandatory.

## Settings Boundary

Vault settings use `Plugin.loadData()` and `Plugin.saveData()`, including the synchronized display refresh-rate preference. Device preferences use `App.loadLocalStorage("inkbook:device-settings:v2")` and `App.saveLocalStorage(...)`; they are local to one device and one vault, not shared across vaults. A valid version 1 value is read once as a migration source and persisted under the version 2 key with built-in canvas shortcuts. `Auto` keeps its measured result weakly associated with the owning window in memory only, observes the main window for the plugin-runtime lifetime, measures each main or active pop-out window once after it becomes visible, and reuses the result across presentation remounts in that live window. It releases pop-out observation with the last presentation and releases the main-window observation when the plugin runtime is disposed. Until measurement completes or fails to produce valid intervals, the effective profile and the Settings status use 120 Hz.

The device-local trusted-document-head ledger uses only `App.loadLocalStorage("inkbook:trusted-document-heads:v1")` and `App.saveLocalStorage(...)`. It retains at most 128 independently validated `{ documentId, revision, outputHash }` records per vault and device, evicting the oldest retained document when advancing beyond that bound. A missing record is established from a validated unlock, and a higher revision advances it. A lower revision or the same revision with another SHA-256 output hash is an explicit external-version conflict and MUST NOT replace the trusted head or activate an editable model. The sole same-revision exception is the exact output of Inkbook's own write after mandatory read-back confirmation, which permits a canonical rewrite to become the trusted head without weakening external-file checks. Malformed, oversized, unreadable, or unwritable ledger state also fails closed. The session integration point is after complete worker validation and before Store adoption on unlock or recovery; successful read-back confirmation advances the same ledger through the persistence observer. Conflict acceptance requires an explicit recovery decision and is not an automatic ledger mutation. Higher revisions cannot prove common ancestry until the file format carries lineage, so branch detection above the trusted revision remains an explicit limitation.

Because the minimum app version is 1.13.0, the settings tab MUST implement `PluginSettingTab.getSettingDefinitions()`. Simple values use declarative controls. The existing nested settings object is retained through typed `getControlValue()` and `setControlValue()` overrides rather than flattened duplicate state. `getSettingDefinitions()` performs no file access or expensive computation. UI validation is repeated by the settings loader because declarative `validate` is not a persisted-data invariant.

Settings UI follows these host rules:

- all visible text uses sentence case
- general rows appear first without a `General`, plugin-name, or `Settings` heading
- later distinct sections use concise headings without the word `settings`
- simple host-rendered rows contain one mutable control; one tool disclosure or visual Page-default row may own its documented group of recognizable controls
- controls save on change; multi-field forms use a modal with Save and Cancel
- reset operations use declarative actions or a bounded render callback and refresh affected definitions
- descriptions remain one concise sentence

The complete settings grouping, disclosure behavior, visual control parity, and validation contract is canonical in [Settings](settings.md#settings-ui). The host adapter MUST preserve the logical General, Page defaults, Drawing tools, Shapes and structures, Snapping, Input, Interface, and Shortcuts groups, while rendering the General rows first without a visible heading. Tool sections use a title with a right-aligned Lucide chevron and the required disclosure accessibility attributes. Settings inherit the neutral Obsidian `SettingGroup` surface and its host-owned radius; they add no nested surface and do not copy an adaptive menu's enclosing border or panel shape. Native host dividers separate independent settings rows, while expanded settings content uses spacing instead of nested separator lines. Within that surface, Settings reuse the Style and Background menu's recognizable swatches, width previews, exact three outline-style buttons, endpoint and dimension icons, table stepper, pattern choices, and slider-plus-number controls. Visual choices fill the available row and wrap only when the viewport cannot contain them; host-specific setting primitives MUST NOT replace these with plain dropdowns when a visual control is specified.

## Commands, Menus, Icons, and Styling

Commands are registered through `addCommand()` with the narrowest applicable `callback`, `checkCallback`, `editorCallback`, or `editorCheckCallback`. Command IDs omit both the plugin ID and a redundant `command` suffix. Commands define no default hotkeys. Names use sentence case and do not repeat the plugin name. Canvas-local actions are not duplicated as Obsidian commands; their device-local bindings and the remaining command inventory are canonical in [Keyboard Shortcuts](keyboard-shortcuts.md).

Inkbook action, settings, keyboard-shortcut, and recovery dialogs use public Obsidian `Modal` elements with native focus and dismissal handling on desktop and tablet. Phone dialogs reuse `AdaptivePanelSession`, the same lifecycle-owned bottom sheet as Style and Background, instead of mounting a native modal shell. They share its grabber, downward swipe, focus containment and restoration, public keymap Back handling, safe-area spacing, internal scrolling, and visual-viewport updates. The sheet is flush with the bottom of the owning visual viewport and uses the shared height limit described below. No separate phone layout or viewport lifecycle is introduced. Initial dialog content is built before mounting; content-height motion does not run during entrance. Durations, reduced motion, and teardown follow the [animation contract](quality-and-testing.md#animation-contract).

Canvas context actions, the selection context menu, toolbar Overflow, and Shape use unmodified Obsidian `Menu` instances. A mouse `contextmenu` uses `Menu.forEvent()`. Touch and keyboard context invocation use `Menu.showAtPosition()` with the owning `Document`. Obsidian owns native-menu placement, keyboard navigation, dismissal, animation, and phone presentation. Inkbook adds no surface class, cloned exit surface, fixed width, host selector, or host-DOM traversal to those menus. The one title-fragment exception is the owned orange text span for Erase all, created through public `MenuItem.setTitle()`. The context menu is populated from the spatial-index result returned by the single presentation-owned canvas input surface; content paths have no listeners and are never browser hit-test targets. All menu and invocation details are defined in [Features](features.md#canvas-context-menus) and [Embed UI](embed-ui.md#native-menus-and-adaptive-panels).

Every standard actionable menu entry calls `MenuItem.setIcon()` with the built-in or registered custom icon specified in [Embed UI](embed-ui.md#context-menu-presentation). Native active choices use `setChecked()`. Delete and Delete embed call `setWarning(true)`, which gives both title and icon the host danger color. Erase all retains its native action and confirmation while its public title fragment and registered `inkbook-eraser-caution` icon use the same orange caution color. Arrange actions remain flat entries without a redundant heading. Menus close on a canvas action, tool change, lock, detach, or unload, and focus returns without scrolling to the invoking control or canvas surface. Obsidian retains complete ownership of phone menu grouping. The only host-wide style exception is the reference-counted phone safe-area fallback: while a menu is open, if the computed `--safe-area-inset-bottom` on the owning document body is smaller than `--size-4-4`, the lease replaces that one token with the menu-padding minimum because the last mobile menu item otherwise has no bottom spacing. The final release restores the exact previous value and priority; equal or larger insets are never changed or incremented. This exception permits no private selector, host-DOM traversal, or other host-style mutation.

Style and Background are the two contents of one Inkbook-owned `AdaptivePanel` component and never mount inside an Obsidian menu item. The component owns its DOM, listeners, timers, observers, focus management, and cleanup through an Obsidian `Component` in the embed's owning document and window. One presentation permits only one native menu or adaptive panel at a time. A native Overflow Background action hands off to the Background panel; Back closes the panel without restoring focus and reopens native Overflow before the next paint. Pattern and spacing changes update the mounted content without closing it. A canvas action, tool change, lock, detach, unload, outside activation, Escape, or Android Back closes the panel.

On wide non-phone presentations, `AdaptivePanel` anchors with the host-native visible gap below the real trigger, flips above when needed, and clamps inside the owning visual viewport. This gap is four pixels on desktop and two pixels on tablet. Desktop uses the host menu background, border, radius, shadow, padding, typography, interaction, and divider variables. Tablet additionally uses the native translucent mobile-menu background, no border, and `--menu-backdrop-filter`. Wide surfaces open and close immediately because Obsidian's desktop and tablet menus have no presence animation. Style uses compact 36-pixel controls in flat sections separated by native dividers. Background content-height changes retain their bounded block-size animation without replaying presence motion. Background Back is a keyboard-operable menu entry rather than a host button, and it and the pattern choices use native menu-item font, icon, gap, radius, and padding geometry. The full-width desktop separator has no inline margin, and the padded S/M/L/XL range uses exact thumb-center label geometry.

When `Platform.isPhone` is true, the same owned component becomes a bottom sheet bounded at the surface by `--safe-area-inset-left` and `--safe-area-inset-right`. It has no border, uses `--touch-radius-s` for its top corners, renders the 15-percent grabber with `--text-faint` and native margins, and applies the greater of the host bottom safe-area and one `--size-4-4` menu inset to its one scrollbar-hidden internal scroll region. The sheet is absolutely positioned against a fixed layer whose complete left, top, width, and height follow `visualViewport`, so resize and offset changes keep it above the software keyboard. Its normal height limit is 60 percent of the keyboard-free viewport height. When the keyboard reduces the visible height, retain that normal limit and clamp only to the full remaining visible height; never apply 60 percent again to the reduced viewport. The surface and its internal scroll region use the same limit. Each session retains the largest observed layout or visual viewport height at the current width and resets that baseline when width changes. If the sheet first opens after both viewport heights have already shrunk, the unavailable pre-keyboard height cannot be reconstructed. On phones only, viewport changes also minimally scroll the active editable field into the sheet's visible internal scroll region after positioning. This correction follows the coalesced viewport update without an additional timed animation, does not scroll the underlying note, and does not override ordinary manual scrolling. A dominant downward touch gesture may begin anywhere on the sheet while its scroll region is at the top; the handle remains draggable from every scroll position. Direction arbitration leaves taps, horizontal controls, and upward content scrolling unclaimed. A claimed gesture tracks sheet translation and backdrop opacity with direct, non-inherited inline properties and without a CSS transition during finger movement. Per-frame updates must not invalidate descendant styles through inherited motion variables; CSS exit variables are populated only once when handing off to the close animation. Regrabbing an entering or settling sheet retains its current visible translation, and release uses the final pointer position before starting exit or return motion. The gesture closes after half the surface height or the bounded velocity threshold, and otherwise animates back from its released position. Reversing the gesture to its origin therefore keeps the sheet open and suppresses the trailing control click. The initial presence animation is owned by a separate one-shot state, so completing an aborted swipe cannot replay the sheet entrance. Phone sheets use the actual public Obsidian `Modal` container and surface to register with the host navigation stack. Android Back therefore requests closing the top sheet; the public keymap and document Escape boundary handle keyboard dismissal separately. Phone sheets retain programmatic initial focus without showing a focus ring, including host box-shadow rings; actual Tab or directional keyboard navigation enables visible focus feedback, and pointer input disables it again. The native history entry remains active throughout the shared exit so repeated Back cannot dismiss an underlying sheet. Owned surface CSS neutralizes native transform transitions while the shared sheet controls translate; final disposal calls the native close lifecycle and removes the public container immediately. Native internal animation cleanup remains host-owned. No private history API, browser-history patch, hidden proxy modal, or additional close button is used. Dialog sheets follow their already-animated disclosure content with automatic height; the adaptive menu height transition must not pin their scroll region or replay a second resize after collapse. Closing makes the panel inert, inaccessible, and pointer-inactive before its surface transition. Phone Style sections use native gray grouped surfaces and 44-pixel touch targets without card staggering. Reduced motion removes every adaptive-panel transition while retaining the same final layout, focus, and dismissal behavior.

The adaptive panel traps sequential focus while open, places initial focus on its first control rather than its dialog container, and restores focus without scrolling to the attached trigger or canvas surface after its final close. Every listener, scope, observer, animation frame, and timer is released on close or unload. Its static CSS is scoped under owned `inkbook-adaptive-panel-*` and content classes; selectors for `.menu`, `.menu-scroll`, or other private host structure are forbidden.

On Android only, the locked activation button receives an owned platform class derived from `Platform.isAndroidApp`. It neutralizes the WebView tap highlight, host hover, active, and ordinary focus surfaces, pseudo-element decoration, minimum button sizing, shadow, filter, and transform while retaining the explicit `focus-visible` outline and the validated SVG. This prevents a host button surface from enlarging or highlighting the locked embed without affecting the active editor or other platforms.

Built-in Lucide icons use `setIcon()`. A custom icon is allowed only when no suitable built-in icon exists and is registered through `addIcon()`. Every icon-only control still has an accessible name and tooltip.

Static styling is authored in responsibility-specific files under `src/obsidian/styles/`; `inkbook.css` is the build entry and imports the motion definitions. The build emits one release artifact, `styles.css`. Styling is scoped below one Inkbook root class except for the single lease-owned scroll-element marker defined above and the owned `inkbook-menu-*` classes mounted by Obsidian outside that root. It uses Obsidian variables such as `--background-secondary`, `--background-modifier-border`, `--text-normal`, and `--interactive-accent`. Runtime geometry uses SVG attributes or narrowly scoped CSS custom properties. Untrusted text is assigned with `textContent` or Obsidian DOM helpers. `innerHTML`, `outerHTML`, and `insertAdjacentHTML` are forbidden.

Obsidian variables style host chrome only. The active document graphic and saved standalone SVG use the fixed self-contained palette in [Standalone SVG Envelope and Theme Rendering](svg-envelope.md), because external editors cannot resolve Community-theme variables. The plugin registers `Workspace.on("css-change")`, reads `App.isDarkMode()`, and updates each mounted presentation's root scheme once through that presentation's lifecycle owner. It does not scan files, rebuild paths, increment revisions, dispatch exports, or write the vault. Reading-view and Live Preview embed hosts expose the same scheme to the embedded SVG through `color-scheme`.

## Community Directory Release Contract

Before a Community directory submission, the repository MUST contain root `README.md`, `LICENSE`, and `manifest.json` files. `README.md` and `manifest.json` now exist, but a license has not been selected. The repository therefore remains private, its package is marked `UNLICENSED`, and it is not submission-ready until an appropriate root `LICENSE` file is deliberately added and verified.

The release contract is:

- manifest `id` uses lowercase letters and hyphens, contains no `obsidian`, and does not end in `plugin`
- manifest `version` and the GitHub release tag are identical `x.y.z` semantic versions
- `minAppVersion` is the actual tested minimum and `isDesktopOnly` remains `false`
- the description is at most 250 characters, ends with a period, contains no emoji, and follows Obsidian capitalization
- `fundingUrl` exists only when it links to financial support
- source contains no sample names, placeholder code, obfuscation, telemetry, self-update logic, dynamic ads, or unnecessary console logging
- the release attaches `main.js`, `manifest.json`, and optional `styles.css`; the production `main.js` is minified and is not committed as source
- `versions.json` records compatibility when release history requires it
- third-party licenses and required attribution are recorded in `LICENSE` or `README.md`
- network use, external vault access, accounts, payments, and other policy-sensitive behavior are disclosed; Inkbook's first release declares none of them

CI uses the official `eslint-plugin-obsidianmd` recommended type-aware configuration and treats applicable findings as errors. Submission readiness is verified from source plus built artifacts; documentation alone cannot establish compliance.
