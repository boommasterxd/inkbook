# Images and PDF Pages

## Import and Local Processing

An active drawing accepts PNG, JPEG and static WebP images and explicitly selected PDF pages. PDF pages become image elements, not editable vector shapes or text fields. Import uses Obsidian's public `loadPdfJs()` renderer without a separate PDF dependency or remote conversion service. Sources stay unchanged. PDF rendering cannot fetch remote font or CMap resources; unavailable local resources are not retrieved from the network. Host renderer limitations can affect PDF fidelity as described below.

Raster import normalizes orientation once, removes source metadata through local canvas encoding, and retains one immutable PNG, JPEG or WebP resource. A source within the separate source limits is decoded once per preparation, then reduced proportionally into one bounded output canvas when necessary. The resize uses the orientation-normalized dimensions and high-quality image smoothing, never enlarges a source, and retains transparency. The original file is not modified. PDF pages render sequentially and share the same output-sizing and encoding policy. Cancellation releases temporary bitmaps, canvases, PDF render tasks and the owned PDF loading task. Import rejects unsupported sources, detected decoding failures and exceeded admission limits before committing elements.

PDF selection uses one-based page numbers and ascending inclusive ranges, such as `1, 3-5`. Duplicate selections are removed and pages are processed in ascending document order. By default, PDF pages retain their proportional writing-width placement and are placed vertically. Standalone raster images initially fit within 40 percent of the writing width in both width and height, without enlarging a smaller source. The optional **Insert at page width and lock** switch is off by default. Its description explains that the locked image acts as a stable background for writing or drawing. It places each image at the left writing-area margin with width equal to the full writing width, preserves aspect ratio, and locks the resulting element. Selected PDF pages remain vertically ordered with one page margin between them. After this placement the selection is cleared, so drawing can begin over the locked pages. The switch changes placement only and does not trigger another source decode or PDF render. Initial element size does not reduce the stored pixels; later resizing remains proportional and uses the same resource. Import-source classification and placement choice are transient; the resulting locks persist under [Element Locks](editor-tools.md#element-locks). An import batch, including its initial locks, commits as one undo step.

The import dialog starts with one compact file picker. A selected source shows its filename, a replace action and a framed preview with pixel dimensions. The button takes its accessible name from its visible text, including the current format or PDF page count and the replace action. Initial source and PDF batch preparation center a spinner above the preparation message; filenames and review content are hidden until preparation finishes. PDF batch preparation identifies the current page below the spinner. Page and resolution changes retain the previous raster and keep the preview navigation and settings usable. One foreground render may run at a time, and rapid changes publish only the latest requested preview. Insert and file replacement are unavailable during a preview refresh. Initial source preparation and batch insertion disable configuration controls while Cancel remains available. A failed refresh clears the stale raster and keeps Insert disabled until successful recovery. A single native animation runs only while preparation is active and the document is visible, stops immediately on completion or closure, and remains static for reduced motion. A separate polite status outside the busy body announces preparation without delaying Cancel. A yellow inline status identifies automatic raster reduction with both original and resulting dimensions; replacing the source clears it. This transient notice is not persisted with the resource. Page selection and preview-page navigation appear only for PDFs; resolution is available for both source types. Expected admission failures identify the relevant file-size, image-dimension, decoding, page-selection or batch-capacity problem without exposing native exception text. Errors reuse the standard inline validation style. Empty status and error regions reserve no visual space. The review shell stays within the available viewport. Wide image and PDF reviews fit their contents up to that limit, with equal spacing on both sides of the footer divider in multi-page reviews. The preview stage keeps a consistent size across page orientations and resolution changes. The body owns scrolling while the Cancel/Insert actions remain visible, including in the phone sheet. Viewport and software-keyboard changes still resize the available surface. Modal entry and exit retain their shared motion owner; review updates do not animate intrinsic dialog height.

Multi-page PDFs place Previous/Next controls and a directly editable current page number with the total below the preview. The footer also shows the output dimensions and actual DPI, wrapping these details below the controls when space is limited. PDFs with at most 20 pages initially select the complete document; longer PDFs select the first 20 pages under the shared batch limit. Only page 1 is initially prepared at insertion resolution; other selected pages are prepared on explicit insertion. Existing aggregate resource limits still apply to the resulting batch. Committing a changed valid import range initially previews its first selected page; subsequent browsing remains independent of the import selection. The primary action names the number of pages to insert. Single-page PDFs omit range and navigation controls. Range drafts update the selected count without rasterizing; only a valid committed preview change can request another full-resolution render. Invalid ranges and preview-page numbers receive inline errors associated with the relevant field and disable Insert until corrected. Invalid preview numbers never reach the PDF renderer, retain the last valid preview, and do not suggest replacing the source file. Page errors and quality warnings remain inside the review shell, with quality warnings beside the settings so they do not move the preview.

The placement preview shows the image relative to the writing area; changing the page-width lock switch updates that local preview without rendering the source again. Once a raster image or PDF is ready on a phone, the sheet uses the available visual viewport above the keyboard. For multi-page PDFs, the source is followed by the preview and its page navigation, the thumbnail chooser and page range, then the resolution and placement options. Raster images and single-page PDFs show the options before the preview. Only the review body scrolls; the title and import actions stay visible. A single-page PDF review fits its contents up to the available dialog height, with no space reserved for page selection. Wide dialogs place the multi-page thumbnail strip under the preview in the left column, with the import settings on the right. On a phone, the optional thumbnail chooser opens directly below the preview and above the page range. Partial thumbnail groups are centered. The editable preview page and total share one field surface, with pixel dimensions and effective DPI grouped below. Each entire thumbnail card, including its preview and checkbox, toggles selection. A short underline marks the current preview, which is controlled by the separate preview navigation. The strip scrolls horizontally by touch or trackpad and offers buttons to move by a group of pages. Selection updates the range without changing the preview and preserves at least one selected page and the 20-page batch limit. The range remains available independently. Thumbnails use the same open PDF, render at most one cancellable background request at a time, and retain at most eight canvases bounded to 144 pixels per edge. They do not encode images or prepare insertion resources. Foreground preview and import take priority.

### Import Resolution

Prepared previews belong to one selected source. Raster profiles that produce the same orientation-normalized output dimensions reuse the same encoded image. PDF entries are keyed by page, requested scale and pixel budget. Each entry retains the page's actual resolution and limit information. Batch insertion reuses reviewed pages in selection order. Missing pages are cached during insertion only if they fit without evicting a later reviewed page. The cache holds at most 20 entries and charges two bytes per Base64 character plus 256 bytes per entry, up to 67,114,144 accounted bytes including padding for individually encoded resources. Decoded canvases, bitmaps and PDF pages are released after preparation. Native decoder and browser allocations fall outside this accounting. Failed preparations are not retained. Source replacement, cancellation and dialog closure release the cache. Each selected PDF page counts against the currently retained session resources, including history, by content ID. Before rejecting a page for capacity, the dialog rechecks the current retained set. The session repeats its authoritative admission check at commit.

The shared profiles are defined in `src/domain/images/image-import-resolution.ts`. **High** remains the initial selection. Raster images retain their original resolution when smaller than the chosen budget; increasing the profile never invents pixels. PDF rendering uses the requested DPI, reduced proportionally when the selected pixel budget or common axis limit requires it.

| Profile   | PDF target | Maximum output pixels |
| --------- | ---------: | --------------------: |
| Standard  |     72 dpi |             2,000,000 |
| High      |    144 dpi |             4,000,000 |
| Very high |    300 dpi |             9,000,000 |
| Ultra     |    400 dpi |            16,000,000 |

PDF previews show approximate actual DPI as well as pixel dimensions. A yellow warning identifies a page whose requested DPI was reduced by the output budget. Higher DPI can improve vector text and graphics, but cannot recover detail missing from a scanned source. The dialog explains that larger rasters consume more memory and leave room for fewer pages. The unchanged 32,000,000-pixel session budget accommodates three distinct A4 pages at 300 dpi or two at 400 dpi before other retained images are counted; different page sizes and encoded-byte limits can reduce that count.

Raster source bytes are read once and retained only while the dialog owns that source. Changing quality reuses a prepared resource when the output dimensions match. Otherwise the dialog reruns the decode, resize, and encode pipeline from the retained bytes. The previous preview remains visible while the new one is prepared. Selecting an unchanged profile and preview page reuses the current result. Insert reuses the matching reviewed resource and renders only the remaining selected PDF pages sequentially. A failed quality change clears the stale preview and disables Insert until a new matching preview succeeds. Resolution controls remain available for recovery. Cancellation or source replacement releases the retained source bytes and owned preview. Ordinary layout, placement and dialog motion changes do not trigger a decode or PDF render.

Before closing the dialog, insertion checks the active session's current resource capacity, including assets retained by Undo and Redo, and atomically commits the prepared batch. A capacity failure is shown inline while the source, selection, resolution, placement and bounded preview cache remain available for correction and retry. Each attempt binds the session revision; cancellation or a revision change during admission prevents publication. A new attempt checks the current revision again. A successful batch remains one undoable operation.

## Element Geometry and Crop

An `ImageElementV3` has the common `id`, `createdAt`, clockwise `rotation` and page-space `pivot`, plus:

```ts
interface ImageGeometryV3 {
  kind: "image";
  x: number;
  y: number;
  width: number;
  height: number;
  assetId: string;
  crop: { x: number; y: number; width: number; height: number };
}
```

`x`, `y`, `width` and `height` describe the visible unrotated page-space box. `crop` describes its visible rectangle in orientation-normalized source pixels. Its origin is nonnegative, its dimensions are positive, and it remains inside the resource bounds. Geometry follows the common canonical rounding and numeric limits in [File Format and Geometry](file-format.md#shared-types).

Images occupy the bottom image band, below all highlighters and other annotations. Selection, move, resize, rotate, arrange, duplicate, clipboard and removal use the existing element command and history paths and obey [Element Locks](editor-tools.md#element-locks). Arrangement changes order only within the image band. Resizing an image or a group containing images preserves proportions and retains a minimum image extent of 0.001 page units. Images are rectangular selection geometry, not connector targets. The eraser skips images; use selection removal to delete unlocked images. A locked image must be unlocked before cropping.

Crop is nondestructive. Applying a crop changes only the element crop and visible box; it neither replaces nor rerasterizes the resource. Retained pixels remain stationary, including for a rotated image. Restoring a larger crop reveals retained source pixels. Choosing Crop replaces the selection overlay directly on the canvas with eight freely draggable edge and corner grips. The frame and grips use the primary chrome accent; corners use L-shaped marks, edges use short bars, and the retained area has no selection tint. The full source remains visible with darkened excluded areas, below highlights and annotations. Dragging inside the crop moves its rectangle within the source. A small neutral pill toolbar provides Cancel and Apply with normal text-colored icons. A visible notice explains that hidden pixels stay in the drawing and can be restored. The owned chrome prefers placement above the image, moves below when there is room there, and clamps against the visible viewport.

Focused grips respond to arrow keys in one-source-pixel steps, or ten pixels while Shift is held. The crop area supports the same keyboard movement. Home restores the full source rectangle, Enter confirms, and Escape cancels. Tab cycles through the crop controls. Accessible instructions describe the keyboard alternatives to dragging. The crop toolbar also exposes the retained-pixels notice to assistive technology. A normal pointer release applies its final source coordinates even when no matching final movement event was delivered. Pointer cancellation or lost pointer capture restores only the crop captured at drag start. Cancel leaves the element unchanged; Apply commits a changed crop as one undo step; an unchanged crop creates no history entry. Normal canvas editing is temporarily disabled while crop controls remain interactive. A document change, owner cancellation or presentation disposal cancels the draft and releases its controls and shared image lease.

The draft retains at least one source pixel and enough pixels to preserve 0.001 page units on each axis after canonical rounding. Preview preparation failures release the crop presentation, controls and active state before rejecting through the existing image-action feedback path.

The source reveal shares the scene's existing image definition and decoder, including for transparent images. Crop feedback visits no other document elements and coalesces draft painting through the central scheduler. Camera changes reposition the controls; live drag and the exact confirmation/cancellation handoff remain immediate. Crop chrome uses the shared short opacity entrance and reduced-motion policy. The underlying scene retains its existing viewport culling.

## Resource Identity and Lifetime

A logical resource has exactly `id`, `mimeType`, `width`, `height` and `data`. `id` is the lowercase SHA-256 digest of the encoded bytes; `mimeType` is `image/png`, `image/jpeg` or `image/webp`; dimensions are positive integers; `data` is canonical Base64. Validation checks the encoded header, declared MIME and dimensions, digest, byte limits and every element binding. WebP validation admits static VP8, VP8L and VP8X containers with matching dimensions, bounded chunks and zero padding; animation flags and ANIM/ANMF chunks are rejected. The native decoder remains responsible for complete bitstream decoding. Conflicting definitions of one ID fail closed. Repeated elements share one resource.

The scene memory estimate covers authored descriptors and DOM bookkeeping. Browser-owned image decoders, SVG instances and raster allocations remain part of native memory acceptance; bounded encoded resources and deterministic work tests do not establish total process capacity.

The active session retains admitted immutable resources, including resources for deleted elements, until session disposal. This bounded first implementation deliberately avoids premature reclamation while Undo and Redo can restore an element. The same aggregate encoded-byte, pixel and resource-count limits include every retained Undo/Redo resource. Consequently, deleting an image does not immediately recover its session resource capacity. Schema validation rejects an over-limit resource set, and serialized session admission rejects an over-limit batch atomically without retaining a partial addition. Repeated references to one content-addressed resource consume the capacity only once; PDF batch preparation uses the same deduplication rule. Saved snapshots include only resources referenced by current elements; a fresh load omits unused resources. Geometry and camera changes reuse existing resources. Scene nodes remain imperative and spatially culled under [Rendering and Performance](rendering-and-performance.md).

Import and clipboard paste stage and validate new resources without publishing them to the session. An instance-owned, single-use preparation token binds the result to its resource owner. Final admission rechecks aggregate capacity against the current retained set. The accepted prepared element mutation publishes its resources before synchronous Store subscribers are notified, without an asynchronous gap. Cancelled, stale, rejected or failed preparations retain no new resources or capacity; existing committed resources remain available to Undo and Redo. The ordinary element mutation, revision and autosave pipeline remains authoritative.

## Capacity and Failure Behavior

The authoritative constants are `IMAGE_LIMITS` in `src/domain/images/image-limits.ts`.

| Capacity                                      |         Limit |
| --------------------------------------------- | ------------: |
| Source file bytes                             |        16 MiB |
| Pixels per raster source                      |    32,000,000 |
| Distinct resource pixels per document session |    32,000,000 |
| Pixels per resource                           |    16,000,000 |
| Width or height per resource                  | 16,384 pixels |
| Encoded bytes per resource                    |         8 MiB |
| Admitted resource bytes per document session  |        24 MiB |
| Resources per document session                |           128 |
| Selected PDF pages per batch                  |            20 |

Byte limits refer to decoded Base64 bytes, not Base64 characters. The complete SVG still obeys the 64 MiB document limit and clipboard payloads the 8 MiB limit in [File Format and Geometry](file-format.md#limits). Raster source headers must satisfy the source byte, pixel and common axis limits before native decoding. Decoded dimensions are checked again before allocating the output canvas. Persisted resources admit up to 16,000,000 pixels while default import output remains limited to 4,000,000 pixels. PDF raster scale is bounded by the selected profile and common resource axis limit. Import preparation and resource admission remain cancellable and use the central scheduler where cooperative work is required. Browser decoding, canvas encoding and an individual host PDF render are native operations with separate cancellation boundaries. The unchanged 32,000,000-pixel admission limit corresponds to 128,000,000 bytes of RGBA pixels, approximately 122 MiB, for one uncompressed copy of all distinct admitted resources. A maximum-sized raster source and its 16,000,000-pixel Ultra output canvas account for approximately 183 MiB of pixel storage before encoding and other allocations. These arithmetic bounds are not total heap limits: browser and host PDF decoders can retain intermediate allocations, additional decoded copies and masks that these public APIs do not expose or bound in aggregate.

Ultra permits approximately 61 MiB for one individual RGBA copy, compared with approximately 15 MiB at the default High budget. It is an explicit import choice; total retained pixel admission remains unchanged. Physical mobile-device evidence for the larger individual working set is not available. Smaller encoded files do not lower the decoded pixel count or establish faster rendering. Increasing this capacity changes no resource fields or SVG grammar; older builds enforcing the former 4,000,000-pixel limit require an update before editing higher-resolution images.

## Encoding and Reader Compatibility

Encoding requests native WebP at quality `1` and compares it with the previous format: PNG for PNG/WebP sources and PDF pages, JPEG at the existing `0.9` quality for JPEG sources. At most two encodes run serially, with the central scheduler's admission check between them. Raster import closes its source bitmap immediately after drawing into the bounded canvas, before either encoder runs. A WebP candidate is selected only when it is smaller, within the byte limit, and its validated container contains a lossless VP8L bitstream. The quality argument alone is not proof of lossless encoding. Only the chosen resource is hashed and converted to Base64. The transient header's lossless flag is not persisted.

Missing, failed, malformed or lossy WebP output uses the previous format. When an unsupported WebP request returns PNG for a PNG fallback, that same result is reused without another encode. The actual returned MIME and binary header must agree. The existing 16,384-pixel axis remains valid; a canvas above the native WebP encoder's 16,383-pixel axis skips the WebP attempt. Encoding does not add another lossy compression step. Native color-space and premultiplication conversions can round RGB values at translucent pixels; the lossless bitstream does not guarantee byte-identical RGBA output across different native encoders. Transparency and graphic content remain part of native SVG/PDF acceptance.

WebP support was introduced as a MIME extension to snapshot version 3 and remains available in the current image format. Current readers retain PNG and JPEG support. Older Inkbook builds that allow only PNG and JPEG require an update before editing files with WebP resources. Locked previews and native PDF export use the same validated self-contained SVG definitions. External viewers need WebP decoding to display those resources. PNG and JPEG remain the baseline formats required by the SVG standard.

## Host PDF Renderer Limitations

Inkbook does not set PDF.js `maxImageSize`: the host renderer can silently omit an oversized source image and still resolve the page render successfully, producing a blank or incomplete page. `stopAtErrors: true` remains enabled, but host-suppressed decoder errors are not fully detectable through the public rendering API. A resolved render is therefore not proof that every PDF source component was reproduced. Check the page preview against the source PDF before insertion.

The 16 MiB source-file, 16,000,000-pixel output-resource and 32,000,000-distinct-pixel session admission limits remain enforced. Selected pages render sequentially, with cancellation and cleanup of owned temporary resources. These limits do not bound every native host decoder intermediate allocation or mask, and Inkbook cannot guarantee a hard aggregate decoder heap limit through the public host API.

## Persistence, Clipboard and Safe SVG

Writers use snapshot version 5 when image elements are present. Earlier version 3 and 4 image documents remain readable. Unlock marks them for canonical rewrite, and the existing autosave schedules version 5 output even without a further edit. Before the first replacement, the exact original is preserved and verified under the [migration backup contract](file-format.md#versioning-and-migration). Clipboard payloads carry only the resources referenced by their selected elements and use version 5 when images are included. Paste remaps element IDs while retaining content-addressed resource identity and commits through the existing atomic paste path. The complete version and compatibility policy is defined in [File Format and Geometry](file-format.md#versioning-and-migration).

A saved SVG embeds each used raster payload exactly once in `defs#inkbook-images`, as an `image` with ID `inkbook-image-<sha256>` and a PNG, JPEG or WebP Base64 data URL. Disk metadata stores matching descriptors without duplicate `data`; validated loading restores the logical resources. Each instance uses a rotation group containing a clipped nested SVG with the crop as its `viewBox` and one local `use` reference. The image group precedes highlights and content. Raster colors are preserved in both themes.

Importing an image or PDF does not change the canvas scheme or selected paint. Auto follows only the document's light or dark scheme and does not detect image brightness or switch at image boundaries. Use the fixed Black color to annotate a light PDF or the fixed White color for a dark underlay; these annotations retain their color across scheme changes. The shared choices are defined in [Settings](settings.md#color-values).

Resource encoding and trusted-output hashing use the bounded native paths defined in [File Format](file-format.md#limits). Raster validation uses strict native Base64 decoding in at most 64-KiB input chunks when available and retains the portable reader otherwise. Both paths reject whitespace, alternate alphabets, invalid padding and nonzero overflow bits, verify decoded lengths, and retain image header, dimension and SHA-256 validation.

The safe-envelope parser accepts only this fixed image grammar, bounded resources and matching local leaf references. It rejects missing resources, invalid crops, duplicate IDs, external URLs, reference cycles and arbitrary image markup. Locked previews import only fully validated definitions and instances into their lifecycle-owned SVG. This extension does not allow general SVG references, external images or executable content. The remaining envelope rules and standalone fidelity contract are defined in [Standalone SVG Envelope](svg-envelope.md#image-extension).
