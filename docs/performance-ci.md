# Performance CI

## Evidence and Acceptance

The gate separates deterministic work/resource/scheduling contracts, relative timing on the same runner, and absolute latency on reference devices. Product budgets and physical-device obligations remain canonical in [Quality and Testing](quality-and-testing.md). A fast development machine or a GitHub runner cannot establish responsiveness on weaker devices.

Local and GitHub CI use one direct-comparison policy. Complete-action tail measurements are the target relative gate inputs. Existing p99, p95, maximum, single-operation, and complete-operation checks remain until a validated enclosing action replaces the internal comparison under [Action Timing Boundaries](#action-timing-boundaries). Block averages and supplemental typical-time medians do not replace or bypass tail measurements. The shared comparison uses the common 1.20 ratio without an absolute relevance floor. A valid but inconclusive comparison produces a visible warning rather than a blocking failure. This changes handling of uncertainty; it does not eliminate physical timing noise or prove unchanged performance.

| Evidence                | Establishes                                                                | Does not establish                                                           |
| ----------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Contracts               | Original scenario behavior, bounded work/resources, controlled scheduling  | Physical speed or device latency                                             |
| Same-runner comparisons | Observed relative costs against the PR base under the stated decision rule | Hardware-independent absolute latency or a whole-suite confidence guarantee  |
| Reference execution     | Original unscaled timing budgets and original populations                  | Browser/GPU/OS/physical-mobile behavior without the prescribed device checks |

## Unified Verification Model

All performance classes and both CI shards follow the same model. A test's protected behavior determines the evidence it needs; refresh-rate classification only determines which profiles execute. Uniformity means common evidence and acceptance rules, not one statistic or one artificial clock for every operation.

| Question                                                           | Required evidence where applicable                                                                                                                                     | Boundary                                                                                                                                                                      |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Does the operation do unnecessary work or retain resources?        | Counts or bounds on visited elements/points, geometry builds, React renders, SVG writes, copied data, retained cache entries/bytes, and owned resources after disposal | Count actual expensive boundaries. A call count or final result alone does not bound work inside the call.                                                                    |
| Does work yield, coalesce, cancel, and prioritize input correctly? | Controlled frame/deadline clocks with assertions on pending frames, work before each yield, cancellation, input pauses, progress, and final completion                 | Simulated time describes scheduling. Extra computation can consume the same simulated time; virtual milliseconds must not be submitted as execution-speed evidence.           |
| Has actual computation become slower?                              | Real elapsed or explicitly labeled CPU measurements compared with the PR base through the shared timing protocol                                                       | Keep typical duration, tail/single-slice duration, and complete-operation cost distinct. A median cannot replace a tail budget; bounded slices alone cannot bound total work. |
| Is the product responsive on supported devices?                    | The prescribed real-Obsidian and reference-device acceptance checks                                                                                                    | Node, synthetic DOM, controlled clocks, and relative CI passes do not establish browser rendering or physical input latency.                                                  |

For new or changed scenarios, record the applicable evidence and unobserved work in the [requirement mapping](#complete-requirement-mapping). Structural-only scenarios do not need an invented timing metric, and synchronous operations do not need a simulated scheduler. Conversely, a noisy timing result does not authorize removing that measurement or treating structural success as proof of speed. Protect buffer reuse and bounded copied elements/bytes at owned boundaries rather than counting every JavaScript array allocation globally. Use multiple fixture sizes when asserting locality or growth behavior.

All selected contracts are mandatory. Required relative comparisons are selected by the shared input planner and use the common [comparison policy](#comparison-policy); benchmarks cannot choose their own tolerance or catch and downgrade failures. Only the shared orchestrator turns valid inconclusive timing decisions into warnings. Every timing metric uses the same relative threshold. A different threshold or measurement method requires predeclared unchanged-code controls and targeted real-source slowdown evidence, with held-out validation and failed or inconclusive results retained. Do not increase repetitions until a result passes or change cold/stateful trajectories into warm microbenchmarks to obtain stability.

This model consolidates the existing gate and authoring rules; it does not claim that every work boundary is already instrumented. The mapping records coverage gaps; [Measurement Limitations](#measurement-limitations) describes the remaining timing uncertainty. Improvements to individual fixtures must follow this same model across all affected profiles. They do not create test-specific acceptance exemptions.

## Action Timing Boundaries

Measure one meaningful application operation per sample, from its trigger through the corresponding scene/DOM update or service completion. Include production dispatch, state/history mutation, downstream callbacks, and scheduled application work required for that outcome. Prepare input fixtures and perform assertions outside the timer. Do not aggregate independent actions into a block or insert unrelated work to lengthen a measurement. Use p99 only with at least 100 separately measured action samples; preserve appropriate maxima or p95 for expensive operations with smaller populations. Consecutive stateful actions need not be statistically independent; paired-process acceptance assumptions remain separate.

A slower internal step is acceptable for the action-speed comparison if the complete action still meets its contract. Keep deterministic limits on actual visited elements/points, geometry builds, node mutations, copies, caches, frame scheduling, yields and cancellation. Equal total duration does not excuse a longer uninterrupted slice: preserve blocking and input-priority obligations for sliced operations. An unchanged action duration cannot prove resource safety.

## Execution

```bash
npm run benchmark
INKBOOK_PERFORMANCE_MODE=contracts npm run benchmark
INKBOOK_PERFORMANCE_MODE=reference npm run benchmark
```

The default command runs the complete gate. Contracts-only and reference execution are explicit local diagnostics and cannot substitute for the complete local or GitHub CI gate. An internal measurement mode uses the fixed PR populations below, real deadline clocks, and action timing statistics while reporting absolute measurements without applying a development-machine latency limit. It is used only by the comparison orchestrator. Legacy hosted multipliers and the former profile configuration are rejected.

The [exhaustive manifest](../scripts/performance-test-manifest.mjs) classifies all 59 gate files and 103 file/profile contract executions: 19 invariant files at 120 Hz, 29 budget-only files at 240 Hz, and 11 cadence-sensitive files at 60, 90, 120, 144, and 240 Hz. Seven serial contract batches use isolated Vitest files and one worker. Every candidate contract runs, including unchanged scenarios. Cadence-sensitive PR-base timing comparisons run only at 120 Hz; invariant comparisons remain at 120 Hz and budget-only comparisons remain at the strictest 240 Hz. Contracts and explicit reference execution retain all five cadence profiles. This reduces repeated measurement work without adding runners; it does not establish execution-speed equivalence across profiles. See the [profile-selection decision](decisions/performance-comparison-profiles.md).

Contracts shorten only pure statistical repetition in clipboard and serialization/export tests. Stateful lifecycles, full-size fixtures, continuous input, and all refresh rates retain their original trajectories. Controlled scheduler time advances by 0.05 virtual milliseconds per checkpoint/read in contract mode; it is not presented as measured speed. Measurement and reference modes use real deadline scheduling. Reference execution retains all original populations. The two expensive domain scenarios use one measured run per comparison process instead of five: transforms retain 50 measured actions after 50 warmup actions; maximum pressure strokes retain 20 measured strokes after 20 warmup strokes, including the original append p99 population. Contracts and reference mode retain all five measured runs and the full capacity assertions. Each domain scenario starts from its own fixture so selective execution cannot inherit mutations from another test.

The manifest identifies 50 files that must supply nonempty timing reports and nine structural/resource files that must supply empty reports. Missing, duplicated, malformed, unexpected, or unsuccessful test results fail. Existing [local contention protection](quality-and-testing.md#coverage-and-ci-gates) remains required. Actual heap checks are runtime-specific; deterministic cache and object limits remain separate.

## Local and GitHub Parity

`npm run ci` executes all local quality checks and the union of both performance shards. GitHub runs `npm run ci:quality` plus `npm run benchmark` with `INKBOOK_PERFORMANCE_SUITE=shared` and `cadence` in parallel. Both routes use the same manifest, contracts, input planner, comparison stages, warning classification and failure rules. No timing scenario is local-only, and p99 is not replaced in either environment. Local execution is serial under the check guard; parallel job distribution does not change coverage.

Unset diagnostic/shard overrides for the full local command. `npm run ci` rejects `INKBOOK_PERFORMANCE_MODE` other than `gate` and `INKBOOK_PERFORMANCE_SUITE` other than `all`; explicit diagnostics or selected shards are development commands, not full CI acceptance. `INKBOOK_PERFORMANCE_BASE` can pin the same immutable PR-base SHA locally as on GitHub. Refresh `origin/main` before relying on the local default; a stale local ref compares different code. A cadence gate selection must include its 120-Hz comparison population; a single non-120-Hz profile is available only in explicit contracts/reference diagnostics.

GitHub quality uses Node.js 24 and performance uses Node.js 26, with the lockfile installed through `npm ci`. Local commands use the active Node executable. To reproduce the same runtime versions, run `npm run ci:quality` under Node.js 24 and `npm run benchmark` under Node.js 26, with the same candidate tree, base SHA and lockfile. Identical policy does not guarantee identical measured outcomes on different machines. GitHub-only repository checks such as `gitleaks` and PR-title validation are not performed by the local npm command.

Both performance jobs have a twenty-minute execution limit. Removing the absolute floor does not add scenarios, repetitions or retries, but more existing comparisons may reach the fixed twelve-pair stage. Exceeding the job limit still fails. Do not raise timeouts or suppress scenarios to accommodate noise.

## Comparison Policy

The [gate](../scripts/performance-gate.mjs) compares with the current PR base, resolved to an immutable SHA for that run. Pull requests use their base SHA; manual dispatches and release gates use `origin/main`. Local gates use `INKBOOK_PERFORMANCE_BASE` when explicitly provided and otherwise `origin/main`. There is no separate historical reference, moving performance tag, or post-merge promotion. The [decision record](decisions/performance-base-comparison.md) explains the trade-off. The reference dependency manifest and lockfile must match the candidate; a mismatch blocks comparison. Both variants receive the same candidate test harness and configuration, with only their source trees replaced. Reports retain resolved commits and source, harness, and dependency hashes, including dirty local input.

The original benchmark files supply comparison measurements directly. There is no second implementation of their scenarios, fixtures, warmup, percentile estimators, maximum windows, or assertions. Missing or changed metric identities and contracts block comparison. Structural assertions remain active while the timing assertion helper records its original measurement.

Source-identical references skip redundant timing, with explicit identity evidence. The [input planner](../scripts/performance-inputs.mjs) can also skip complete original test files whose resolved transitive test/fixture/source input graphs match. This optimization requires verified identical dependencies and the reviewed Vitest configuration hash. Configuration changes, unresolved imports, dynamic source loading, filesystem reads, and external source edges conservatively require measurement. All candidate contract files still execute.

Changed files run in separate normal-V8 processes for reference and candidate. Both sides use identical selected scenarios, profiles, fixed PR populations, and clocks; they never share a heap. Measurement runs disable Vitest results caching. The graph-only esbuild configuration preserves value-form type imports, while opaque or unresolved inputs conservatively require comparison.

All candidate contracts execute first. Their timing records identify exact `(file, testName)` scenarios for the initial comparison; structural-only tests are not repeated in measurement mode. Every selected scenario must execute successfully and provide the expected metric identities and contracts, including ordinals and budgets. Missing scenarios, unexpected execution, missing or extra metrics, and execution failures block the gate. Scenario selection requires independent fixture state, not hidden setup from preceding tests.

The fixed plan has two decision points: six paired runs and, only for unresolved scenarios, twelve in total. Each stage predeclares three AB and three BA pairs in randomized order. After six pairs only scenarios with an unresolved metric repeat, retaining their complete action populations and all their metrics. Already decided metrics remain decided; other completed scenarios do not rerun. No decision is taken between stages and there is no retry after twelve pairs. Valid unresolved results become explicit warnings. More extensive investigation is manual, not another automatic CI job. See the [bounded-plan decision](decisions/performance-bounded-measurements.md).

For each matched pair of positive measured statistics, compare `candidateMs / baseMs` with the common `1.20` boundary (20 percent). There is no absolute minimum increase, budget-derived relevance floor, per-test tolerance or hosted timing multiplier. The same rule applies to p99, p95, maxima and complete-operation totals. Existing reference-device budgets remain unchanged and are enforced separately in explicit reference mode.

Six of six ratios strictly below the boundary establish pass at the first stage; ten of twelve establish pass at the final stage. The symmetric strictly-above rule identifies regression. Exact ties, zero measured durations and insufficient directional evidence remain inconclusive; zero observations are never silently discarded. Decisions reached after six pairs remain frozen. The sign test evaluates the median of paired reported-statistic ratios; it does not replace each trajectory's p99 with a sample median. Action samples within retained runs remain intact; process and inner-run populations follow the fixed plan above.

| Evidence                                                                                                      | Local and GitHub behavior                                                                |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Valid comparison classified `pass`                                                                            | No timing warning or blocking violation                                                  |
| Valid comparison classified `regression`                                                                      | Blocking violation and nonzero exit                                                      |
| Valid comparison classified `inconclusive`                                                                    | Visible warning, comparison remains inconclusive, no blocking violation from that metric |
| Missing, malformed, incompatible or unexpected evidence; contract/test failure; timeout; report-write failure | Blocking violation or thrown error and nonzero exit                                      |
| Verified identical source or complete transitive inputs                                                       | Explicit identity proof; not a measured timing pass                                      |

Warnings never suppress another metric's regression or an infrastructure failure. After the existing final stage, do not retry an inconclusive result until green. An unresolved metric in a batch already rejected for a regression may be reported at the first stage; the job still fails. A valid zero duration is uncertainty, while absent or invalid telemetry is an error.

`performance.json` retains raw comparisons with their original `status`, plus separate top-level `warnings` and `violations` arrays for completed evaluations. Warnings include metric identity, paired ratios, boundary and evaluated stage. Local and GitHub logs print `WARNING`; GitHub additionally receives a warning annotation. Successful command completion means no blocking failures, not that every timing comparison passed. Reports with execution errors preserve the error and available evidence. A failed or truncated execution must never be converted into a timing warning.

A nonblocking warning accepts the risk that a real regression cannot be resolved within the fixed measurement budget. The relative margin and finite measurements can also admit smaller slowdowns that accumulate across merges. Deterministic work/resource contracts and absolute reference-device acceptance remain independent safeguards. The [timing-warning decision](decisions/performance-timing-warnings.md) records why the absolute relevance floor was removed.

The fixed two-look sign test retains its one-sided false-pass bound of `1/64 + 79/4096 = 0.034912109375`, assuming independent, comparably distributed process pairs under the null of a median paired ratio at least 1.20. This bounds classification as `pass`, not the probability that a regressed change can merge: warnings are also nonblocking. It is not a simultaneous guarantee across metrics. Reports retain raw `ratios`, the common `regressionRatio`, stage-specific ratio median bounds and decision counts. Obsolete statistic-selection metadata is rejected. See [NIST's sign-test definition](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/signtest.htm). Scheduler and platform dependence remain.

### Total work for sliced operations

A slice-duration check alone cannot detect every slowdown: deadline-limited work can require more equally long slices. Additional relative-only records compare the sum of already measured active work for complete replacements, endpoint fan-out, dense erasing, eraser finalization, wire preparation/adoption, and each worker-fallback operation. Existing p95/p99, slice maxima, absolute budgets, and deterministic work assertions remain. CPU-time and elapsed-time sums are labeled separately and never combined. Repeated complete-operation totals retain their existing runs; where a maximum is reported, it is the maximum of complete-run sums, not the longest single slice.

The [recordRelativeTiming](../test/performance/timing-assertions.ts) helper records existing durations without invoking operations again or inventing an absolute budget. These records use `comparison: "relative"` with `referenceMs`, `limitMs`, and `ratio` set to `null`, and a stable nonempty label. Both the report parser and comparator reject mixed absolute/relative contracts and label drift. The shared ratio rule and warning/error classification apply; these are complete-operation costs, not block averages. Reference-device runs retain every existing absolute check; relative-only records do not establish new absolute latency guarantees.

### Timing boundaries

Worker fallback records use high-resolution monotonic elapsed time at operation start, yield, resume, and finish. Owned `setImmediate` waits are excluded; external preemption during active spans is included. The p95, maximum, and complete-operation sum share this clock. Other benchmarks explicitly labeled CPU time retain their own clock.

The cross-format UTF-8-versus-cloned-string test retains its full 8-MiB fixture, one warmup, five balanced sample pairs, and transfer/adoption assertions. Its strict winner assertion is a reference-device requirement, not a PR regression metric: unchanged Node code can change the cross-format ranking. CI still compares the actual production request-packing and result-adoption timing records against the PR base. Descriptive annotations are not persisted timing evidence.

## Measurement Limitations

Earlier ratio-only unchanged-source controls left some original p99 measurements inconclusive, including coalesced pen input, internal frame and endpoint fan-out measurements. The isolated live-stroke handoff also showed noise. The removed 0.1-ms relevance floor reduced local inconclusive results but could hide repeated relative slowdowns in short operations. The current policy reports valid uncertainty without widening the permitted slowdown. This is not proof of noise-free measurements for these or other paths. An experimental complete-action replacement was rejected because its repeated execution exceeded the then-current ten-minute CI runtime requirement. Its additional benchmark and diagnostic infrastructure have been removed. Existing comparisons remain active. Running both sides in one process, native-module execution, and fixed extra whole-test warmups did not establish a reliable replacement. None is part of the gate. Do not add alternative block kernels, pool warm trajectories as cold samples, change V8/GC behavior to obtain a pass, or retry until green.

A speed regression exclusive to 60, 90, 144, or 240 Hz can escape the cadence-relative gate when deterministic contracts still hold. Five-profile contracts verify scheduling and work/resource behavior, not speed at those omitted timing profiles.

Source or transitive-input identity is valid evidence that unchanged runtime inputs need no comparison. It is not evidence that the timing method is stable. Report source-identical contract duration separately from changed-source comparison duration. A green quality/contract run that skips timing must never be described as a successful unchanged-code timing control.

Future measurement changes require predeclared unchanged-code controls and targeted slowdowns, including occasional slow frames that exercise p99 sensitivity, followed by independent validation and a measured CI-time impact. Preserve raw failed and inconclusive results. Deterministic work-bound checks do not detect every form of additional computation, and the current relative gate does not guarantee detection of every rare pause.

Synthetic DOM and Node workers do not measure browser layout, paint, compositor, GPU, operating-system input, or physical mobile responsiveness. All original absolute product budgets and reference-device checks remain required; an arbitrary local computer is not automatically a reference device.

## Hosted Execution and Evidence

Preserve required checks `CI`, `Performance (shared)`, `Performance (refresh profiles)`, `gitleaks`, and `Validate PR Title`, standard Ubuntu runners, quality Node 24, and performance Node 26. Shared and cadence shards run in parallel on separate runners; benchmark work within each shard is serial. Post-merge main pushes do not repeat the tested squash tree. Release tags rerun the complete gate.

Raw measurements, failures, input identities, and comparison decisions remain available as job artifacts for one day. No later run depends on those artifacts; the next gate measures its base source on the same runner. Local default evidence is retained outside disposable workspaces. Time/output limits bound the harness and must not be interpreted as product latency budgets. Source-identical CI duration must be reported separately from changed-source duration.

The quality job and both performance jobs have twenty-minute execution ceilings, including setup, selected checks and evidence upload. Exceeding the limit fails the job; this is neither proof of successful completion within twenty minutes nor permission to omit checks or retry failed comparisons. Runner queue time is additional. Each benchmark subprocess also has a twenty-minute safety timeout in both local and hosted execution; this does not impose a twenty-minute total limit on the complete local command. The hosted job ceiling covers all its subprocesses together.

## Adding or Changing Performance Tests

1. **Define the protected behavior.** Place benchmarks under `test/performance/<source-area>/` and reuse representative fixtures from the owning area or `test/fixtures/`. State the operation, input size, expected result, and applicable product budget from [Quality and Testing](quality-and-testing.md). Preserve full-capacity fixtures, stateful sequences, and cancellation/disposal checks. A small fixture or correct final result alone does not prove bounded work.
2. **Assert work and resources independently of elapsed time.** Observe actual expensive boundaries through test adapters, spies, or instrumented fixture data: visited candidates/points, geometry builds, DOM writes, pending frames, retained entries/bytes, and released resources. Derive limits from the contract, not the development PC. Where locality or complexity matters, vary unrelated data or fixture size to expose full scans or quadratic work. Do not mock away the production operation being protected or introduce production behavior solely for counters. Record any cost that the counters cannot observe.
3. **Keep scheduling and speed separate.** Use controlled frame/deadline clocks to exercise coalescing, yielding, cancellation, and bounded work per slice. For fallback scheduling, reuse [createFallbackDeadlineClock](../test/performance/persistence/fallback-deadline-clock.ts): only contracts mode uses virtual checkpoint time; measurement/reference use real time. Virtual milliseconds are not latency measurements. Keep counters and semantic assertions active in every mode; place costly resource inventories outside timed operations or in a separate complete resource test.
4. **Report real timing through the shared helpers when needed.** Use [expectTiming](../test/performance/timing-assertions.ts) with the original absolute budget instead of adding direct machine-dependent elapsed-time assertions. It enforces absolute limits in reference mode and reports measurements for relative comparison. For continuous interactions, reuse [INTERACTION_REFRESH_PROFILE, measureInteractionFrames, and interactionP99](../test/performance/interaction-refresh-profile.ts); p99 requires at least 100 samples, and smaller populations report their maximum. Keep test names, timing-call order, optional labels, and budgets stable across compared variants. Preserve the intended warmup, action sample population, timing boundaries, and statistic. A changed process population requires a predeclared plan, unchanged-code controls, slowdown evidence and explicit documentation; do not reduce repetitions dynamically to obtain a pass. Do not create a second benchmark implementation for the reference tree.
5. **Register execution and telemetry.** Add each file to exactly one class in the [manifest](../scripts/performance-test-manifest.mjs): `invariant` when the profile changes neither workload nor budget; `budgetOnly` when only the monotonic budget changes; `cadenceSensitive` when deadlines, timestamps, simulated frames, or production inputs change. Add files emitting timing assertions to `TIMING_PERFORMANCE_FILES`; structural-only files stay out. Missing required telemetry and unexpected telemetry both fail. Update the complete mapping below and inventory totals when adding/removing files or changing class. Keep unrelated expensive timing scenarios in separate files when their source dependencies differ, so the input planner can prove identity independently. Cadence classification requires all five contract/reference profiles, while the recurring relative comparison uses 120 Hz; additional recurring timing profiles require a reviewed policy change and measured cost evidence.
6. **Preserve comparable inputs.** Import production code and fixtures through resolvable dependencies so the input planner can establish unchanged graphs. Opaque inputs conservatively trigger measurement; never manually skip a test merely because it appears unrelated. The candidate harness also runs against the PR-base source tree, so new tests must execute meaningfully against that source. If a new API or dependency change prevents that, report the incompatibility and resolve the comparison design explicitly; do not silently skip the comparison or weaken acceptance.
7. **Use the common decision policy.** Do not add direct wall-time merge assertions, per-test thresholds, warning suppressions, or different local/hosted behavior. An inconclusive comparison is nonblocking only when inputs and telemetry are valid; missing evidence, thrown errors and timeouts must still fail. Keep raw failed and inconclusive controls. Do not describe a warning as a timing pass or a deterministic contract as proof of speed.
8. **Verify detection and integration.** Run `npm run benchmark` and the required `npm run ci` checks for executable changes. The contracts-only command above is useful during development but is not complete acceptance. For a new work bound, demonstrate that a targeted extra-work/resource regression fails, using a disposable mutation or a focused negative fixture; remove temporary mutations afterward. For a new timing scenario or changed measurement method, predeclare the measurement budget and ordering, then inspect same-source controls and relevant real-source slowdowns, including rare slow actions for p99. Use held-out validation for measurement-policy changes. Preserve raw measurements and report inconclusive outcomes; do not widen tolerances to make controls pass or treat one successful control as a suite-wide false-alarm guarantee. Update the mapping with what is actually observed and its limitations. Physical latency claims still require the prescribed reference-device checks.

For a concrete combined example, [chrome-refresh-profile.test.ts](../test/performance/rendering/ui/chrome-refresh-profile.test.ts) measures continuous updates and independently asserts one root render plus cleanup. [path-cache-remount-performance.test.ts](../test/performance/rendering/scene/path-cache-remount-performance.test.ts) demonstrates resource and cache bounds without a timing gate. Reuse the closest existing scenario rather than copying the CI orchestrator.

The [statisticalSamples](../test/performance/sample-policy.ts) helper may shorten only repeated statistical trials in contracts mode when one trial still covers the complete behavior. It must not shorten stateful trajectories, capacity fixtures, lifecycle soaks, or refresh-profile coverage. Measurement and reference modes retain the original counts. Do not add hardware multipliers, fit product budgets to local timings, or treat a fast desktop as evidence for weaker devices. Relative decision thresholds and stages are owned by Comparison Policy, not individual benchmarks.

The exact-base save callback has its own invariant file with the same full serialized fixture, callback, warmup, sample count, and 8-ms budget. This adds one fixture serialization per invocation but lets input selection and second-stage repeats run the callback without unrelated full/incremental/order-only worker exports. It does not shorten those worker scenarios.
