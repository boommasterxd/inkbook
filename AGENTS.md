# Project Instructions

## Scope and Architecture

Inkbook is a desktop- and Android-capable Obsidian plugin that overlays retained SVG annotations on native Markdown views. Obsidian owns Markdown, editor history, workspace lifecycle, settings hosting, and Vault access. Inkbook owns annotation domain records, deterministic geometry and binding logic, view-local projection, sidecar persistence, and recovery.

Dependencies point toward framework-independent domain modules. Domain code must not import Obsidian, CodeMirror, React, DOM, storage, or worker APIs. Application modules coordinate commands and ports. Rendering, input, UI, workers, and Obsidian adapters implement outward concerns. Cyclic dependencies, process-global mutable state, per-element React scene components, and direct file-system access are forbidden.

## Simplicity Guardrails

Implement the smallest production behavior that satisfies the current phase. Keep limits and ownership with the subsystem that allocates the resource. Do not split one local responsibility into generic coordinator, ledger, handle, profile, admission, and accounting layers when a bounded counter or owner object in the existing module is sufficient. A new cross-cutting service requires at least two current independent consumers plus a measured invariant that local ownership cannot enforce.

Production and test paths use stable product or domain terminology from their introduction. Roadmap phases and requirement IDs MUST NOT define source modules, test directories, fixtures, runtime identifiers, commands, CSS classes, schemas, or storage keys. Extend the nearest existing module and mirrored test suite before creating another file. Temporary probes or migration scaffolds require a named removal deliverable and MUST NOT become permanent architecture.

## Performance Priority

Performance and resource efficiency are Inkbook's highest technical optimization priority. Every architecture and implementation choice MUST optimize and measure interaction latency, main-thread work, allocation and retained-memory cost, framework and DOM work, and avoidable I/O. Correctness, data integrity and recovery, security, and accessibility are non-negotiable and MUST NOT be traded for speed.

The plugin MUST remain fully interactive at the 5,000-element minimum tier and pass the predeclared 10,000-element stress tier on the named supported desktop and Android device matrix. Preserve retained, viewport-bounded SVG; minimal imperative projection diffs outside React; zero per-element React scene components; zero React note-root commits on pointer, gesture-preview, scroll, zoom, culling, retained-node, selection-chrome, and worker-progress paths; incremental spatial indices and work proportional to affected elements or viewport candidates; worker-first DOM-independent computation at the specified admission thresholds; and hard bounds on queues, bytes, concurrency, caches, slices, mounted nodes, path commands, and lifecycle resources. A single-element operation MUST NOT scan or rebuild the complete scene.

Performance is a phase-exit and release gate for product paths implemented in that phase. Countable complexity, ownership, queue, allocation, and disposal properties belong in the existing deterministic unit and integration suites with compact generated fixtures and test-local thresholds. Add wall-clock, presentation, paint, heap, touch-driver, or thermal measurements only when the corresponding product path exists and a stable automated host or device exposes the required signal. Normal CI output and production-package checksums are sufficient records by default. Do not create a separate performance profile, evidence schema, manifest, validator, runner hierarchy, profiling build, or plugin-wide resource ledger unless measured product behavior proves that the existing test, build, and subsystem-local limit mechanisms cannot enforce the requirement. Missing physical automation leaves only the physical claim unverified and MUST NOT become a recurring user measurement procedure. [`docs/specification/06-svg-rendering.md`](docs/specification/06-svg-rendering.md), [`docs/specification/09-quality-and-performance.md`](docs/specification/09-quality-and-performance.md), [`docs/specification/10-testing-and-acceptance.md`](docs/specification/10-testing-and-acceptance.md), and [`docs/specification/11-implementation-roadmap.md`](docs/specification/11-implementation-roadmap.md) remain authoritative for budgets and verification.

## Naming and Documentation

Technical content, identifiers, comments, tests, configuration, and documentation use English. Source identifiers and file names use ASCII-compatible English names. Documentation lives under `docs/`, uses `kebab-case` Markdown file names, and links to the authoritative owning specification instead of duplicating contracts. Update this index whenever a Markdown document under `docs/` is created, moved, renamed, or removed.

Documentation is not executable test evidence. Verify documentation through review, formatting, and link consistency. Do not create documentation-test suites, generated requirement inventories, traceability matrices, governance fixtures, placeholder evidence manifests, duplicate status systems, or scripts whose only purpose is to restate or mechanically inventory prose requirements.

## Quality Limits

Review functions above 50 lines, files above 300 lines, cyclomatic or cognitive complexity above 15, functions above 4 parameters, and nesting above 3 levels. CI fails above 100 function lines, 500 file lines, cyclomatic complexity 20, cognitive complexity 25, 6 parameters, nesting depth 4, or below 85 percent line coverage. Exceptions must be narrow, measured, and justified.

Prefer immutable records, closed discriminated unions, small public interfaces, explicit lifecycle ownership, bounded queues and caches, stable callbacks, incremental indices, viewport-bounded work, retained SVG updates outside React, and worker-first DOM-independent computation. Correctness, security, accessibility, and maintainability remain release gates alongside performance.

## Tests and Tooling

Tests live under `test/`. Create subdirectories only when real product suites need them. Every relevant behavior change requires deterministic normal, boundary, failure, race, and abuse coverage. Prefer extending the existing unit, integration, fake-host, browser-simulation, and build suites. Add a new runner, harness, fixture hierarchy, result schema, or test-only abstraction only when an implemented behavior cannot be observed faithfully through existing tools and the new structure is smaller than the duplication it removes. Critical editor, persistence, recovery, multi-pane, Android, accessibility, and performance workflows require integration or end-to-end tests at the lowest faithful automated layer. Fixed waits are forbidden.

CI must enforce formatting and linting with the quality limits, strict static type checking, automated tests, at least 85 percent line coverage, `jscpd` with `minTokens: 50`, `knip`, dependency security auditing, architecture-boundary checks, and the production build. Add integration, accessibility, Android, and calibrated performance gates only when the corresponding implementation and executable environment exist. Reuse `npm run ci` and direct package inspection before adding another command or framework. Do not add placeholder evidence systems or weaken gates through broad exclusions or unexplained suppressions.
